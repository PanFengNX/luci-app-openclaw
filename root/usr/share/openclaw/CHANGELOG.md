## 1.8.57

修复第三轮深度审计发现的备份、恢复和状态锁问题，并调整模型按需安装与模型列表来源。

### 备份与恢复

- 加密备份现在额外包含 `secure/delpass`、`cloud/pass`、`cloud/home/`、`cloud/bin/` 普通文件，以及程序目录中的 provider/skill 插件文件，恢复后尽量保持原设备的密钥、登录态和组件可用。
- 备份归档升级为格式 2；恢复目标仍由当前设备路径推导，不覆盖本机 `base_dir`、`state_dir`、`openclaw_dir`，旧归档保持兼容。
- 扩展凭据复制失败时中止备份，避免生成“看似成功但缺少 Key”的残缺归档。
- 恢复失败或恢复后的网关无法启动时，回滚数据目录和 `cloud/bin`；归档路径校验拒绝符号链接、硬链接、设备、FIFO、绝对路径和 `..` 路径。
- 修正 GNU tar 与 BusyBox tar 清单格式差异，避免合法归档因字段位置不同被误拒。

### 模型与状态锁

- 新安装默认不预装 DeepSeek 或 Z.AI；已有 `preinstall_providers` 配置升级时不覆盖。用户在模型页选择 provider 并应用时，才按 provider 处理插件和配置。
- 模型页直接请求当前 provider 的 `models_url`；实时请求成功时显示 API 模型，失败时仅显示随包预设并提示可能过时，不再从本机 OpenClaw 获取模型列表，也不再显示“（上游）/（本机）”后缀。
- `recover-lock` 检查结果区分：无锁可继续、官方检查完成但需人工确认、CLI 不可执行或结果无法确认；不自动杀 PID、不手工删除锁、不自动执行 `--confirm`。
- 新增锁状态和模型来源回归测试并纳入全量回归；第三轮深度审计报告见 `docs/AUDIT-2026-10-30-round3.md`。

- 全量回归：**111 通过 / 0 失败 / 1 跳过**。
- 备份归档安全测试：**11 项全部通过**；锁状态测试全部通过；Shell 语法、Lua 解析和三种包格式验证通过。

## 1.8.56

修复 2026-10-30 第二轮深度审计发现的 P1 路径、维修和临时目录问题。
完整报告见 `docs/AUDIT-2026-10-30.md`。

### 修复

- **普通 repair 会绕过 root-only 权限加固**：`repair.sh` 之前直接对整个安装目录递归 `chown -R openclaw`，会重新把 `secure/delpass`、`cloud/pass` 和 `backups` 交给服务用户。普通 repair 与 `owner-fix` 现在都会调用 `oc_harden_root_paths`。
- **repair 不识别自定义 `main.state_dir`**：现在只计算一次 `oc_state_dir()`，配置、状态锁、doctor 的 `OPENCLAW_STATE_DIR` 和外置状态目录权限修复都使用同一目录。
- **repair 对外置 state_dir 缺少安全校验**：在任何递归权限操作前，对 `BASE` 和 `DATA` 都执行同等强度的 fail-closed 路径校验；危险系统路径或符号链接路径不会被触碰，也不会回退到默认目录。
- **路径校验漏过中间符号链接**：`lib.sh` 和 `init.d` 现在逐组件检查已有路径，最终叶节点不存在的正常新目录仍可创建，已有中间/末端符号链接拒绝。
- **LuCI 私有临时目录安全边界不足**：`/tmp/.openclaw` 现在要求 root 上下文、root 属主、真实目录和 0700 权限；预置符号链接、普通文件或非 root 目录 fail-closed。

### 回归验证

- 新增 `tools/tests/p1-fixes.sh`，实际执行 lib.sh 与 init.d 的路径校验函数；修复前代码反向运行时安全路径断言失败，修复后通过。
- 全量回归：**105 通过 / 0 失败 / 1 跳过**。
- shell 语法检查通过；Lua 使用 `luaparser` 解析通过；三种包格式构建与结构校验通过。

### 已知未完成项

- `cloud/bin`、`cloud/home` 的完整属主模型仍需真实 OpenWrt 与 bdpan 流程验证，本版没有贸然修改，以免破坏云组件登录和更新。
- 本轮未处理 P2 项（备份解析器 no-follow、api_run 命令形状、未收录云组件哈希、timeout 降级、全局 core_pattern、过期 dist-web 页面）。
- 当前 Windows/MSYS 测试环境无法创建符号链接，相关测试项明确显示 skip；需在 OpenWrt/Linux 环境补做。

## 1.8.55

修复 2026-10-29 全盘深度审计发现的两个 P0 级与三个 P1 级缺陷。
完整审计报告见仓库 `docs/AUDIT-2026-10-29.md`。

### 修复

- **备份恢复的定时任务与插件清单从来没有恢复过**（P0）
  `backup.sh` 的 `cmd_restore()` 在读完数据目录后立刻回收暂存区，
  而定时任务段与插件清单段在此之后才去读 `$stage/crontab.txt` /
  `$stage/plugins.txt` —— 目录已不存在，两个分支恒为假。
  后果：恢复备份后「定时备份」的 crontab 行不会写回，云备份静默停止，
  用户以为已恢复。git 追溯显示该功能自诞生起就是死代码，从未生效过。
  现在回收动作移到两段处理完成之后；失败路径仍由既有的 EXIT trap 清理。

- **删除密码哈希与云备份口令被交给服务用户**（P0）
  `lib.sh` 的 `oc_fix_perms()` 对安装目录整体 `chown -R` 给 `openclaw`，
  把 `secure/delpass`（删除密码哈希）和 `cloud/pass`（云备份加密口令）
  也一并交了出去，而代码注释明确写着这两项应为 root 属主。
  现在在递归操作之后追加 `oc_harden_root_paths()`，把 `secure/`、
  `cloud/pass`、`backups/` 收紧回 `root:root`（目录 0700 / 文件 0600）。
  每步失败只告警，不影响服务启动；顺序是「先保证网关可写，再收回不该给的」。

- **改删除密码时状态查询失败会跳过旧密码校验**（P1）
  `openclaw.lua` 用只取 stdout 的 `sh()` 查 `delpass-status`，退出码被丢弃。
  查询失败返回空串，于是「已设置密码 → 必须验证旧密码」的分支被整段跳过，
  任何人打开页面都能重置保护。现在先判退出码，查不到状态就拒绝本次修改。

- **下载备份不检查符号链接**（P1）
  `api_backup_download` 直接用 `io.open` 打开备份文件。若归档目录里被人放进
  一个指向系统文件的符号链接，LuCI 以 root 运行会跟随链接把目标读出去。
  现在打开前先 `lstat` 判链接（`stat` 跟随链接，`lstat` 不跟随——必须用后者），
  取不到 `lstat` 时按 fail-closed 拒绝。

- **`main.state_dir` 实际从未校验**（P1）
  `init.d/openclaw` 里 `_state_dir_safe()` 只有定义、没有调用点。
  把数据目录填成 `/etc` 之类的系统路径不会被拦截。
  现在按该文件既有的 fail-closed 口径（与服务用户不存在、数据目录属主不对
  同一口径）拒绝启动并给出修复命令；刻意不回退到默认目录，避免既有数据目录
  被静默换掉。校验位置在启用判断之后，未启用时不误报。

### 回归测试

新增 `tools/tests/audit-2026-10-29-fixes.sh`（已并入 `tools/verify-project.sh`），
对上述三处做行为级实测而不是静态字符串断言——这三处都是「代码看着对、
实际没生效」的死代码型缺陷，静态断言抓不住。已用修复前的代码反向验证过：
三项全部 FAIL，修复后全部 PASS。

### 未处理（已知限制，需真机验证后再动）

- 云组件安装器未收录的 sha256 只告警不拒绝（P2-1）：改成默认拒绝会阻断
  「插件还没更新、云组件已发新版」这一种正常场景。
- `api_run` 命令白名单按首个子命令放行（P2-2）：细化到完整命令形状容易误伤
  `mcp` / `devices` / `pairing` 的真实用法。
- 启用 core dump 会改写全局 `/proc/sys/kernel/core_pattern`（P2-3）：默认关闭，
  仅排错时临时打开。
- 上传备份把整份读进 Lua 内存（P2-4）：LuCI 的 `http.formvalue` 无法流式读取。
- `cloud/` 目录本身仍归服务用户（P0-2 的延伸）：收紧它需要确认服务用户是否
  要写 `cloud/home`，贸然改可能直接让云备份失效，故本轮不动。

## 1.8.53

**修复插件自更新在 apk 系统上永远装不上的问题，并加固网关 token 的随机性。**

### 1. 更新检查/安装不再报「无法获取当前安装文件列表」

`apk info -L` 输出的是**不带前导斜杠**的相对路径（apk-tools 源码 `DIR_FILE_FMT`
即为 `"%s%s%s"`，无前导 `/`），而插件里取清单的 awk 只接受 `/` 开头的行（那是
opkg 的格式）。在 OpenWrt 25.12 / iStoreOS 25.12 这类用 apk 的系统上，回滚清单
恒为空，安装被直接中止 —— 这就是从旧版本升级时"更新失败"的真正原因。现在：

- 清单归一化同时接受相对路径与绝对路径（剥掉前导 `/` 后统一成相对路径）；
- `apk info` 失败时改为直接读已安装库 `/lib/apk/db/installed` 的 `F:`/`R:` 记录兜底；
- 丢弃 `..` 段、以 `-` 开头的行（避免被 `tar -T` 当成选项）与空行；
- 回滚包的 `.sha256` 现在会校验摘要格式，无效则中止安装而不是留下坏校验文件。

### 2. 不再报「无法生成候选标识（随机源不可用）」

`oc_rand_hex` 原来只认 `od` / `hexdump` 两条路，某些 busybox 构建上这两个工具
选项不全就整体失败。现在兜底顺序为
`od → hexdump → sha256sum(临时文件) → md5sum(临时文件)`：

- 摘要兜底先把随机字节落到私有临时文件、核对长度，再对**这同一份数据**求摘要，
  避免短读/空输入变成固定值；
- 输出必须是 64 位小写十六进制才采用，长度对了但内容非法照样丢弃；
- 临时文件在所有路径（成功、失败、长度不符）都会删除；私有目录不可用时不再
  退化到文件系统根或可预测文件名，而是整体失败。

### 3. 网关 token 不再可能是弱随机值

- 删除 `/dev/urandom` 不可读时基于 `awk srand()` 的弱随机回落 —— 随机源取不到
  就整体失败，宁可失败也不产出弱凭据；
- `install.sh` / `repair.sh` 共 5 处生成 token 的地方全部补上判空：失败时中止
  并给出明确原因，绝不把空 token 写进配置；
- `repair.sh` 补齐 token 时改为**先拿到 token 再改 `auth.mode`**，避免随机失败时
  留下"mode=token 但没有 token"的半截配置导致网关起不来。

### 4. 定时备份「启用」勾选不再消失（显示问题）

备份页打开时走的是合并端点 `cloud_overview`，它把 `schedule.enabled` 输出成
**数字 `1`/`0`**，而保存后回读的 `schedule-status` 输出的是 JSON 布尔
`true`/`false`。前端判定是 `d.enabled === true`（严格相等），数字 `1` 不等于
布尔 `true`——于是**保存是成功的（crontab 行在），但重新打开页面勾选框被清空**。
现在 overview 的 schedule 输出与 schedule-status 完全一致（布尔 enabled、
补上 keep_local），新增 `tools/tests/cloud-overview-schedule.sh`（6 项）盯住
两个端点的字段集合与类型。

### 5. 回归测试

新增 `tools/tests/github-update-filelist.sh`（21 项，已纳入 `tools/verify-project.sh`）：
覆盖 apk v3 / opkg 两种清单格式、已安装库兜底、随机标识的四条兜底路径、
失败路径的临时文件清理、以及"送进摘要的就是那已核对长度的 32 字节"的行为证明。


## 1.8.52

**备份本地与云端都留存；修复备份列表对大归档的卡顿。**

### 1. 定时备份不再只留云端（需求变更）

此前定时备份上传成功后会**删除本机副本**——网盘账号失效或断网时本地
反而没有可恢复的备份。现在本地与云端一样按份数轮转：

- 新增配置 `main.cloud_keep_local`（界面「定时备份 → 本地保留份数」），
  默认 **2**（当前一份 + 上一份），可设 0-30；**0 = 不保留本地**（旧行为）
- 打包前先把旧副本轮转到 N-1 份腾位置（避免空间预检失败连云端备份都
  做不成），上传后再兜底轮转一次压回 N 份总量
- 手动「立即备份到云端」本来就保留本地副本，行为不变
- 老配置没有这个键也能跑（代码侧默认值），升级无需迁移

### 2. 备份列表卡顿修复

列表接口统计归档大小时原来用 `wc -c`——会把整个归档**从头读一遍**，
2.5GB 的备份在路由器存储上要几十秒，接口超时后页面看起来就是
「本地备份一直不出 / 卡住，过一会儿又好了」（页缓存热了就快了）。
改为 `stat -c %s`（O(1) 元数据读取），列表创建、手动云备份的体积显示
同步修正。

### 3. 新增回归测试

`tools/tests/cloud-local-keep.sh`（15 项，纳入 `verify-project.sh`）：
本地轮转的删除份数、except 保护（本次归档绝不删）、keep=0 不动任何
文件、非匹配命名不碰、含空格目录、目录不存在，以及源码级防回归
（backup-run 两处调用、cmd_list 不再用 `wc -c <`）。

## 1.8.51

**全盘审计发现并修复的三类问题（都有界面表征，不是理论风险）。**

### 1. 只读端点没登记 → 功能静默失效（最严重）

控制器的 CSRF 守卫按「路由短名」查 `READ_ONLY` 表，表里缺/写错名字时，
那个用 GET 调用的只读端点会直接被要求 POST —— 不报错、不崩溃，只是某个
功能**永远不动**：

- `gh_update_status` 是**拼错的登记**（真实端点叫 `github_update_status`）；
- `cloud_backup_poll` 从未登记 → 云端备份进度读不到；
- `delpass_status` 从未登记 → 备份页「删除密码」永远停在**读取中…**。

三者已修正，并新增 `tools/tests/api-readonly-route.sh`（已纳入
`verify-project.sh`）把这张表盯住：既有「僵尸键」检查，也有「前端 GET
调用的端点必须在表里」检查，不再靠人眼核对。

### 2. 轮询缺闸门 → 无限重试、界面卡死

- 云端备份轮询：`r.ok === false` 时旧逻辑会当成空结果继续排下一次，
  于是每 1.5 秒重试一次、永不停止，界面卡在「备份中」。加了连续失败上限
  （5 次）与总时长上限（约 5 分钟），命中即释放 busy 并给出提示。
- 诊断弹框：关闭按钮只隐藏弹框，定时器继续每 2 秒请求、两个按钮仍禁用 ——
  任务若没走到 done，「体检」「一键修复」就再点不了（即「点了没反应」）。
  现在关闭会停轮询并放开按钮；轮询另加网络失败上限与总时长上限。

### 3. 界面细节

- 秒表元素 `.oc-elapsed` 补上等宽数字样式（此前无 CSS 规则，数字宽度变化
  会把旁边的按钮推来推去）。

### 体检结果：相对一线的部分（无问题，记录备案）

- JS 引用的元素 id、页面按钮的事件绑定、视图使用的 API 端点注册情况：全部对齐；
- `q()` 单引号转义、`run` 子命令白名单、凭据只走 `--key-file`：均到位；
- `rm -rf` 带变量的分支都有 `${var:-}` / 非空守卫；诊断后端已有陈旧 worker
  保护（返回 rc=124）。

### 1. 新增插件自更新（检查 + 手动确认 + 回滚）

安装页新增「插件更新」区块，只认固定仓库 `PanFengNX/luci-app-openclaw`：

- **检查**：读 latest Release，逐段数字比较版本（`1.8.9 < 1.8.10`，支持 `v`
  前缀，tag 解析不出来就不判为有更新）；候选结果存成**一份原子快照**
  （写临时文件后 `rename`），安装只读这一份，不会读到「A 版本的版本号 +
  B 版本的资产名 + 第三个 digest」这种撕裂组合。
- **资产匹配**：只接受当前平台的确切文件名（apk-tools v3 用
  `luci-app-openclaw-<ver>-r<数字>.apk`，opkg 用
  `luci-app-openclaw_<ver>_all.ipk`）；`-v2` / `-signed` 之类变体一律拒绝。
- **必须校验**：Release 的资产 digest 或校验和文件里必须能找到本资产的
  SHA256，**找不到就拒绝安装**（不回退到「来源可信，所以放行」）。下载有连接/
  总超时、8MiB 上限，落在 0700 私有目录。**下载物只交给 apk/opkg，不执行**。
- **先备份再动手**：安装前把当前已安装文件打成回滚包并写 `.sha256` sidecar；
  备份失败就不下载、不安装。回滚时先校验 sidecar、复制成私有快照、再校验
  归档条目（拒绝绝对路径 / `..` / 符号链接 / 硬链接 / 设备），然后
  `apk del` / `opkg remove` 再按清单还原 —— 不用 `tar -x` 直接覆盖，
  那样会留下新版本独有文件造成新旧混杂。
- **不静默升级**：检查、安装、回滚都是用户点击触发；安装/回滚是 POST +
  二次确认。后台 worker 记录**真实 pid**，锁用 `mkdir` 原子获取，
  owner 已死才回收，无 pid 的锁一律不抢（否则会与刚建锁的 worker 并行）。

### 2. 纠正 1.8.47 的状态锁处理（这条是上一版的方向性错误）

1.8.47 加了「读锁里的 pid，`kill -0` 失败就 `rm -f` 锁文件」。查官方
gateway-lock 文档后确认这是错的：

- 锁在 `$OPENCLAW_STATE_DIR/tmp/openclaw-<uid>/state.<hash>.lock`；
- 崩溃 / SIGKILL 之后，启动过程**会自行回收**确认已死的 owner；
- 需要人介入时必须 `openclaw gateway recover-lock` 拿 fingerprint，
  再 `--confirm <fingerprint>`，由它在**独占状态所有权**下同时清 sidecar
  与 SQLite owner lease；
- 官方原文明确写着不要手工删锁文件（*instead of removing lock files by hand*）。

只删 sidecar 不清 lease，会让数据库留着指向死 pid 的租约，而后续连
recover-lock 要核对的指纹对象都没了 —— 状态可能更僵。

**现在的做法**：`oc_clear_stale_state_lock()` 只调用官方检查命令，
把 fingerprint 打进日志给人确认；**任何情况下都不删锁、不自动 `--confirm`**。
检查不通过时 repair 跳过本轮 `doctor`（否则 doctor 会去抢同一把锁，
把「维护中」吞成普通 WARN）。启动路径仍只清真正的一次性临时根
（`$base/tmp`、`/tmp`），永不触碰 `state_dir/tmp`。

### 3. 网关凭据判定收敛到一处（修 SecretRef 误判的根因）

之前同一份配置形状在 init / repair / install / cli 各写一遍，用了三种解析器
（jsonfilter、匹配大括号、grep），结论互相打架。现在统一到
`/usr/libexec/openclaw/credential.sh`，产出五态：

| 状态 | 含义 | 是否启动 |
| --- | --- | --- |
| `PLAIN` | 明文凭据 | 是（无空白才导出到环境变量） |
| `REF` | `source` + `id`/`name` 的 SecretRef | 是（**不导出**，网关自己解析） |
| `BADREF` | 有 `source` 缺 `id`，或结构化值没有 `source`（如 `{}`） | 否 |
| `MISSING` | null / 空串 / 字段缺失 | 否（token 模式） |
| `UNREAD` | 配置读不了 / 解析器缺失 / JSON 坏 | 否 |

顺带修掉两个真实缺陷：

- `grep '[[:space:]]'` **检测不到换行**（grep 按行匹配，LF 是分隔符）。
  含 LF 的明文因此会被判成「干净」导出到环境变量，实际已被截断。改为
  空格/Tab 用 `case`、CR 用运行时构造、LF 用 `wc -l`，三类分别检查。
- `jsonfilter ... | head -n1` 会把含换行的凭据静默截成第一行，
  「半截凭据」看起来仍是合法明文。改为完整取回再判空白。

密码模式同样按官方建议走环境变量，不放 `--password`（会出现在 `ps` 里）；
`--auth` 跟随配置里的 `gateway.auth.mode`（none/token/password/trusted-proxy），
未知值直接拒绝启动，不再静默钉死成 token。

### 4. 自动 doctor 不再以 root 跑

schema 落后时自动执行的 `doctor --fix` 以前是 root 直跑，会往 state 里写
root 属主文件（网关随后 EACCES），且看不到服务用户的插件。改为
`su -s /bin/sh $OC_USER -c ...` 以服务用户执行，脚本体固定、路径走位置参数
（不拼进 shell 代码）。

### 5. 其它

- `usr/bin/openclaw` 的 PATH 在 source 库**之前**就补齐 `/sbin:/usr/sbin`，
  否则非 root 服务用户找不到 `/sbin/uci`。
- `repair.sh` / `install.sh` 改用共享判定，只在 `MISSING` 时补 token，
  不再覆盖已有的 `REF`。
- 前端更新状态轮询有上限（连续 3 次失败或 5 分钟即停并恢复按钮），
  不再出现永久转圈。

回归断言 345 → 356 项，另新增凭据形状矩阵 19 项（在目标 shell 下实跑）。

## 1.8.47

**修复升级到 OpenClaw 10.x 后网关起不来、一键修复也救不回来的问题。**

三个独立缺陷叠在一起，任何一个都会让网关停在「停止」状态：

### 1. 状态所有权锁被我们自己的清理逻辑删掉（最致命）

OpenClaw 2026.10 起把网关 / `doctor` / 离线 SQLite 维护的锁统一放在
`$OPENCLAW_STATE_DIR/tmp/openclaw-<uid>/state.<hash>.lock`。这个位置和
「临时目录」同名同路径，但它是**锁**，不是缓存。

我们的清理函数会扫 `$state_dir/tmp` 并删掉不属于服务用户的
`openclaw-<uid>` 目录。删除时如果维护进程仍持有该锁，数据库里就留下一条
指向已消失进程的租约，此后：

```
OpenClaw state at .../openclaw.sqlite is undergoing offline maintenance
by sqlite-maintenance process <pid>; retry when it finishes.
```

而那个 pid 早已不存在 —— 网关拒绝启动，`doctor` 也拒绝执行，形成死锁。

**修复**：清理函数只扫真正的临时根（`$base/tmp` 与 `/tmp`），永不触碰
`state_dir/tmp`。

> ⚠️ 1.8.48 修正了本节的一个错误方向：当时还加了「pid 确认已死就删锁文件」，
> 那是错的。OpenClaw 官方 gateway-lock 文档明确要求不要手工删锁 —— 只删
> sidecar 不会清掉 SQLite 里的 owner lease，反而让后续连 recover-lock 要核对
> 的对象都没了。1.8.48 起改为只调用官方 `gateway recover-lock` 做检查，
> 任何状态下都不删锁文件。

### 2. SecretRef 形式的 token 被误判为「没有 token」

token 若是密钥库引用 `{"source":"store",...}`，代码识别后会把变量清空
（正确，不能当明文塞进环境变量），但紧接着的判据是 `[ -n "$token" ]` ——
于是引用被当成「没有」，日志报 `未生成网关 token，拒绝启动`，
而配置里明明有 token。升级到 SecretRef 后必然踩到。

**修复**：判据改为「变量为空 **且** 不是 SecretRef」才拒绝。

### 3. 删除密码永远显示「读取中…」

`dpApply()` 有两处调用，数据形态不同：`delpass_status` 给 JSON 字符串，
`cloud_overview` 给的已经是对象。原代码无条件 `JSON.parse`，对对象会抛异常
并回退成 `{}`，`typeof d.set === 'boolean'` 永远为假 → 永久「读取中」。

**修复**：先判类型再解析。

### 4. 登录状态误判（顺带）

百度 `whoami --json` 返回的是 `{"authenticated": true, ...}`，
而判定器只认 `logged_in` / `isLogin` 等键，于是已登录也被判为「无法确认」，
云端备份列表因而不显示。**修复**：把 `authenticated` 纳入布尔判据。

回归断言从 333 项增加到 345 项，逐条锁住上面四个分支。

## 1.8.44

**备份页刷新慢、一直「读取中」：4 次脚本启动 + 一次联网调用。**

### 原因有两层

**第一层：页面加载要启动 4 次 `cloud.sh`。**

`status` / `pass-status` / `encrypt-status` / `schedule-status` 各是一个端点，
每个端点都独立执行一次 `cloud.sh`。而它是 lib.sh 2060 行 + 本体 3900 行 ——
**每启动一次都要把 6000 行 shell 解析一遍**。路由器上这不是可以忽略的开销，
而且 4 个请求还会排队抢 uhttpd 的 worker（默认 worker 数很少）。

**第二层：`status` 里的 `bdpan whoami` 是联网调用。**

它有 25 秒超时，失败还会再试一次不带 `--json` 的 —— 也就是最坏 50 秒。
而它**完全没有缓存**，每次打开页面都跑一遍。网盘侧慢或不通时，
光这一项就能把页面卡到几十秒。

### 改法

**① 合并成一个端点。** 新增 `cloud.sh overview`，一次脚本启动返回
`status` + 加密 + 口令 + 删除密码 + 定时设置的全部状态。前端从 4 个请求
变成 1 个。为此把前端的四个状态函数拆成「应用」与「拉取」两层，
这样 `overview` 一次拿回结果后逐个分发（否则它得复用会再发请求的旧函数）。

**② 状态缓存。** `status` 的结果缓存 30 秒（`OC_CLOUD_STATUS_TTL`），
安装 / 更新组件、登录、登出都会立即让缓存失效。要实时值时传 `--fresh` ——
所以「刷新」按钮用的就是它，因为用户点刷新就是不信缓存。

新鲜度判据用 `oc_mtime`（`stat -c %Y`），**不用 `date -r`**：
busybox 的 `date` 没有 `-r`，配上 `|| echo 0` 会静默得到 0，
age 恒等于当前时间，缓存永不命中。这个坑在版本列表缓存里已经踩过一次。

### 实测发现并修掉的一个真问题

`overview` 是把 `status` 的 JSON 剥掉外层再拼三个子对象。但 `status`
**失败时**输出的是 `{"ok":false,"error":"..."}`，格式与成功时不同 ——
`sed` 剥不掉，于是拼出：

```
{"ok":true,{"ok":false,"error":"网盘组件未安装",...
```

这是**非法 JSON**，前端解析失败后整页状态全空。而「组件未安装」恰恰是
最常走到的路径（刚装上插件就是这个状态）。现在先判 `cmd_status` 的 ok 值，
失败就整包失败并透传原来的 error。两条路径都用真实 JSON 解析器验过。

### 顺带修掉 1.8.43 的一个疏漏

`dpStatus()` 定义了但**从未被调用** —— 删除密码状态会永远停在「读取中」。
现在它由 `overview` 分发（`dpApply`），状态能正常显示了。

## 1.8.43

**删除要密码、本地与云端合成一个列表、备份有秒表、口令走弹窗。**

### 删除备份需要密码（服务端强制，不只是前端弹框）

本地删除与云端删除都过同一道闸门 `delpass_gate`。**前端弹框只是交互**——
直接构造一个 POST 就能绕过，所以校验必须在控制器里做。

这是一个**只用于删除**的密码，与加密口令完全独立：

| | 加密口令 | 删除密码 |
| --- | --- | --- |
| 用途 | 解密备份内容 | 确认「你同意删除」 |
| 能否还原原文 | 必须能 | 永远不需要 |
| 存储 | 明文 0600（否则解不开） | **只存加盐哈希** |

合成一套的后果很具体：改了删除密码，用旧口令加密的备份就再也解不开了。

实现要点：
- 存储 `secure/delpass`，目录 0700、文件 0600，内容 `<alg>:<hex>:<salt>`；
- **算法随哈希一起存**——某天系统补上 `sha256sum`，之前用 md5 存的密码还得能验；
- 口令只经 stdin 进哈希，**不进 argv**（`/proc/<pid>/cmdline` 全局可读）；
- 先写同目录临时文件再 `mv`，中断不会留下半截密码文件（那会让用户既删不掉也设不了新密码）；
- 验证失败固定 `sleep 1`：这个接口能被脚本反复调用，6 位口令的搜索空间不大；
- 改密码、清除密码**都要先验旧密码**——否则谁打开页面都能先把保护关掉。

而且**本地行没有「上传」按钮**——想要云端有一份，只能重新打一次包。

现在一个列表、按时间倒序、每行带来源标记：

```

[云端]  openclaw-backup-2026-10-25-0300.tar.gz   11.8 MB   恢复 删除
```

「先本地备份，再上传」这条路径现在是完整的。

`clEmptyList` / `clFmtTime`）。它们还在往已删除的 `#cl-list` 里写，
页面加载后会在控制台抛 null 错误。**其中 `clDelete` 还绕过了新加的删除密码**，

### 备份过程中的秒表

秒表按区块区分（`#bk-elapsed` / `#cl-elapsed`）：不分的话，云备份跑起来时
本地卡片也会跳秒，用户会以为两边都在跑。

### 加密口令的设置与清除改成弹窗

## 1.8.40

**临时根身份错位：按 Hermes 的实机验证修复。**

### 机制（读 OpenClaw 源码 + 实机验证，不是我猜的）

`resolvePreferredOpenClawTmpDir()` 的解析顺序：

1. 试 `/tmp/openclaw` —— 合格判据两条：属主 == 当前 uid，且 `mode & 0o022 == 0`
2. 不合格 → 回退 `$TMPDIR/openclaw-<uid>`，同样要求属主 == 当前 uid
3. 再不合格 → **硬失败**，一切需要状态的操作被拒

于是现场那个故障的完整链条是：

1. wrapper 给 **root 上下文**设了 `TMPDIR=$BASE/tmp`（VAR 域内）；
2. root 的 fallback 临时根就生在 `$BASE/tmp/openclaw-0` —— **VAR 域内部**；
3. 此后任何一次 `chown -R VAR` 把它翻成服务用户；
4. root 再跑 → `has owner uid 998, expected uid 0` → **永久被拒**。

### 三处修复

**① `/tmp/openclaw` 钉成 `root:root 0700`**（`oc_pin_system_tmp_root`）。

属主与权限位要一起钉 —— 判据含 `mode & 0o022 == 0`，光改属主不够。
放在**服务启动路径**（`procd_open_instance` 之前），因为 `/tmp` 是 tmpfs，
重启即失，只在装包时做一次没用。

钉好之后：root 永远命中 preferred（**不在 VAR 里造目录**），服务用户走自己的
`$TMPDIR/openclaw-<uid>`（落在磁盘，日志因此持久，而不是留在 tmpfs 里重启丢失）。

**② root 上下文不再设 `TMPDIR`**（wrapper）。这是故障的起点，必须断掉。
`TMPDIR=$BASE/tmp` 只允许出现在**以服务用户运行**的命令串里。

**③ 清理判据改为「basename 必须是 `openclaw-<纯数字>`」。**

我 1.8.37 写的清理用的是 `openclaw-*` —— Hermes 实测**误删了 9 个目录**
（`openclaw-update-report-*`、`openclaw-update-run-handoff-*`、
`openclaw-<date>.log` 都在同一层）。

先改成 `openclaw-[0-9]*`，但实测发现它**仍然会命中 `openclaw-2026-10-25.log`**
（日期也以数字开头）。靠 `[ -d ]` 挡掉文件不够 —— 判据要独立成立，
不能依赖"它恰好是文件"。现在用 `oc_is_tmp_root()`：拆出前缀与后缀，
后缀必须非空且全为数字。实测判定：

```
openclaw-0                ✓ 是临时根
openclaw-998              ✓ 是临时根
openclaw-2026-10-25.log   ✗ 不是
openclaw-update-report-x  ✗ 不是
openclaw-                 ✗ 不是
```

### 结构性改动：启动路径不再做 `chown -R`（I4）

这条是「修了反而起不来」的根治。原来启动时会「属主探测 + 条件 `chown -R`」，
两个问题：

- 判据是 **root 视角**（`stat -c %U`）。root 对被 root 拥有的 0755 目录永远可写，
  所以这类判据只能看出「属主名字不对」，看不出「**服务用户实际打不开**」。
- 判据只看**顶层**属主。内部被 root 写过的文件（doctor 以 root 跑就会产生）
  不会被发现；一旦发现就退回全树 `chown -R` —— 7~8G、几万文件、几十秒，
  还可能与正在运行中的网关抢同一批文件。

现在启动只做 O(1) 断言，并以**服务用户身份**跑真实写入探针；
失败就 fail closed（不启动），并打印一条可直接复制的修复命令。
真正的属主修正只发生在显式维护路径：**`repair.sh owner-fix`**（新增）。

### 顺带

- `core_pattern` 从 `$base/logs`（VAR 域）改到 `$base/dumps`（DIAG 域，
  `root:root 0700`）：core 的属主取决于崩溃进程，留在用户域里会制造
  「非服务用户属主的文件」，清理还得动用户域。
- 启动日志固定打印 `user=... base=... state=... tmp_root=...`，现场一眼可查。
- 安装收尾以服务用户身份自检，失败即判安装失败 —— 与其「装完了但网关起不来」，
  不如装不上并说清原因。
- `oc_as_user` 的命令串内补 `cd $HOME`：root 从 `/root`（0700）调用时，
  su 之后 cwd 仍是 `/root`，子进程 chdir 失败，只报一句与权限无关的
  `Command failed during launch or output capture (EACCES)`。

## 1.8.35

**「无法升级」的根因，以及按官方文档补齐升级流程。**

### 根因：陈旧锁永久挡住升级

`install-bg` 用的是裸 `oc_locked()` —— 它只判断**锁目录是否存在**。
于是任何一次被 SIGKILL、OOM、断电打断的操作都会把目录留在那里，
此后**每一次升级都被"另一个操作正在运行"拒绝**，用户除非知道要
`cli.sh unlock`，否则再也没有升级入口。

改为 `oc_lock_busy()`（问"有没有**活着的**进程持锁"）。陈旧锁交给
`install.sh` 里的 `oc_lock_acquire` 原子接管 —— 那里本来就有完整的
陈旧判定和 `mv` 抢占，只是升级入口绕过了它。

### 顺带：借鉴 iStore，升级入口自己清理残留

升级入口不该假设"上一次是干净结束的"。现在 `install-bg` 启动前会：
清掉陈旧锁、清掉上一次的完成标记 / rc / pid / start / logpath、
把上一次的日志移成 `.1`（**不删**，那是失败的唯一现场）。
剩下真正在跑的 `install.sh` 由 `oc_inst_alive` 拒绝 —— 这个拒绝是对的。

### 按官方文档补齐三处（此前都没有）

查了 `docs.openclaw.ai/install` 与 `install/updating`，我们缺三步：

1. **`--allow-scripts=openclaw`**。npm 12 默认**阻止**未批准的 package
   lifecycle scripts，而 OpenClaw 的 `preinstall` / `postinstall` 正是这类；
   不显式批准会被 blocked，表现为"装完了但跑不起来"。
   但 npm ≤11.15 没有这个选项、带了会直接报错，所以按版本探测：
   `>=12` 必加、`11.16+` 也加、`<=11.15` 绝不加。
2. **`openclaw doctor --fix`**。官方安装器在升级已有安装后必跑
   （`--non-interactive`，best effort）。不跑的后果很具体：`openclaw.json`
   的 schema 随版本演进，不修的话升级完可能起不来或功能异常，日志里只有一句
   `config invalid`。已插入为独立阶段（阶段总数 7→8）。
3. **`sharp` 的 `SHARP_IGNORE_GLOBAL_LIBVIPS=1`**。官方安装器默认设，
   避免它在路由器上尝试对系统 libvips 做原生构建（必然失败或极慢）。

另外补了官方升级序列的最后一步 **`openclaw gateway status --deep`**：
端口通只说明进程在听，不说明网关自己认为健康（插件加载失败、schema 未迁移完
都可能仍然监听）。结论记进安装日志。

### 拒绝也要留痕

`install-bg` 的三条拒绝路径（base_dir 不安全 / 有锁 / 已有安装进程）此前
只写 stderr 就 `exit 2`，**不创建也不写日志**。于是面板打开"升级日志"只能
显示"暂无安装日志"，用户完全不知道被拒的原因。现在拒绝也写一行进安装日志。

交互反馈与备份完整性：

  进度条、结束切绿/红并显示状态。原来是默认收起的内嵌小框，用户点完不知道有没有开始。
  弹窗有自动滚动（往上翻会自动关掉）与复制。

- 安装页的「安装」按钮此前**没有任何确认**，点下去直接开始下载几百 MB。

**升级卡死（真 bug）**
- `api_install` **无条件返回 `ok:true`**。而 `install-bg` 有三条同步拒绝路径
  （base_dir 不合法 / 已有操作在跑 / 已有安装进程），都只写 stderr 就 exit 2，
  而 `sh()` 刻意丢弃 stderr —— 拒绝原因彻底消失，后台进程压根没起来，
  前端却以为已开始，`install-status` 永远查不到 running。改用 `run_capture`
  拿退出码，把真实原因回给前端。

  （`OC_CRONTAB` 在 backup.sh 里原本未定义，一并修掉。）

## 1.8.31

**修复 1.8.28~1.8.30 一直存在的致命错误：所有接口 500。**

1.8.28 我把 57 个端点从 `call("api_xxx")` 改成了
`call(guarded("xxx", api_xxx))`，想用一层包住来加 POST 校验。但 LuCI 的
`call()` **只接受字符串函数名**：

```lua
local function _call(self, ...)
    local func = getfenv()[self.name]     -- 按名字查环境
    assert(func ~= nil, 'Cannot resolve function "' .. self.name ..
           '". Is it misspelled or local?')
```

传函数对象进去，`getfenv()[函数]` 得到 `nil`，assert 直接抛异常 ——
**每一个 API 请求都 500**。而页面模板不走 `call()`，所以界面能正常渲染，
只是所有数据都读不到：挂载点空、程序位置永远「读取中…」、版本列表
「服务无响应」、模型下拉空、网盘状态失败。

1.8.29 我修的是同一个函数的另一个独立缺陷（`out` 的前向引用），
没有触到这条，所以症状照旧 —— 这次用真实 Lua 5.1 把每条路由跑了一遍才定位到。

修法：注册改回 `call("api_xxx")`；POST 校验改为在文件末尾把包环境里的
`api_*` 统一换成守卫版（`getfenv(1)[name] = guarded(name, fn)`）。
集中式校验保留了，但不再试图把函数对象塞给 `call()`。

新增两项回归（都接进 `verify-project.sh`）：

- `tools/tests/lua-dispatch.py` — 静态检查，`call()` 的参数必须是字符串字面量，
  且不能指向文件局部函数（`getfenv()` 看不到局部函数）。
- `tools/tests/lua-dispatch-run.py` — 用真实 Lua 5.1（`lupa`）加载控制器，
  模拟 LuCI 的 `module`/`entry`/`call`/`_call`/`setfenv`，把 **57 条 API 路由
  逐条 dispatch 两次（GET + POST）**，任何一条抛异常即失败。

对照验证：修复前 57 条全部失败，修复后 57 条全部通过。

这类错误的共同点值得记住：**语法合法、单元测试通过、页面能渲染，只有真正
调度一次才会暴露。** 所以这次不是再改一遍代码，而是补上了能跑的验证。

## 1.8.30

按设备实测报告（附 /proc、ubus、/proc/<pid>/limits 的原始输出）修复：

- **网关在跑却报「已停止」**：`oc_gateway_pids` 的判据是「argv[0] 恰为私有 node
  二进制」，但网关启动后 Node 把 `process.title` 改成 `openclaw-gateway`，Linux
  上这会**直接改写 argv[0]** —— `/proc/<pid>/cmdline` 只剩一个 token，
  `comm` 也被截断成 `openclaw-gatewa`，所以 `pgrep -x node` 与旧的 argv 比较
  双双失效。主判据改为 `basename(argv[0]) == openclaw-gateway`，遍历 `/proc`
  而不依赖 pgrep，保留 node+gateway 作为兼容分支。
  连带修好：状态页状态、`oc_kill_tree`（原来空转，卸载会删运行中程序的目录）、
  以及安装前的停服门。
- **安装的停服门从未触发**：`/etc/init.d/openclaw running` 走 `procd_running` →
  `ubus call service list`，而这台机器的 ubus 没有 `service` 对象（连不存在的
  子命令都返回 0）。改用进程表判定，这是唯一可信来源。
- **非 root 下 CLI 全废**：`/tmp/.openclaw` 属主是 root，非 root 调用时直接
  「拒绝继续」，连 `status`/`info`/`token`/`log` 都跑不了，锁也拿不到。
  改为回落到 `$HOME/.openclaw-run-<uid>`（二次校验属主），root 仍收回原目录。
- **SecretRef 被当成明文 token**：`get_token()` 只判非空、不判形状，把
  `{"source":"store",...}` 原样返回。面板把它拼进 `#token=` URL，用户登录必然
  失败，而且留在浏览器历史里。现在识别该形状并如实返回空，前端提示改为
  「由密钥库托管」而不是「获取失败」。
  同理 init.d 不再把 SecretRef 导进 `OPENCLAW_GATEWAY_TOKEN` 环境变量。
- **日志页会永久挂住**：`logread` 在某些 iStoreOS 构建上既不返回也不报错，
  无超时会占死 CGI。加 5 秒超时，失败时告知真实日志路径。
- **core dump 开关实际无效**：`procd_set_param limits core="unlimited unlimited"`
  会被按空格拆成 soft/hard，而 soft 位只认数值或单个 `unlimited`，结果
  `soft=0` —— 等于一直关着（同机 unetd/hostapd/netifd 用单值都正常）。
  改为单值。
- **pidfile 只删不写**：加 `procd_set_param pidfile`，`running()` 的兜底分支
  从此有意义。
- `openclaw-task.log` 追加前不轮转（全仓唯一漏掉的写口），会吃 tmpfs 内存。
- `/var/log` 对网关用户不可写时，`oc_log` 静默丢日志；改为回落到
  `<安装目录>/logs`。
- rpcd ACL 补上 task / backup 日志与轮转文件的读权限（面板原来读不到）。
- `cli.sh` 里描述 `--force` 能清理占端口进程的注释与实现不符，已改写。

- 覆盖安装前先停服务，收尾用 `restart`（`start` 对运行中的实例是空操作）。

- 云端备份的暂存目录从 `/tmp`（tmpfs）改到数据盘，并用硬链接树代替整份
  `cp -a`。这台机器数据 7.8G、tmpfs 仅 4.2G 可用 —— 原来的配置下备份**每天必失败**。
- 还原不再把备份里的 `/etc/config/openclaw` 整份写回：只搬端口 / 绑定 / 镜像源 /
  云备份计划等非路径项，路径类保留本机值（否则属主修复会对着错路径白做）。
- 还原改为「起服务并等到端口应答才算成功，失败自动回滚到还原前数据」，
  不再先删旧数据再起服务。
- 卸载改用专用端点并检查返回值：原来前端发的是后端白名单里没有的
  `cmd=uninstall`，必失败却无条件报「已提交」，而且先把服务停了。
- 15 个写端点在入口层统一要求 POST（此前 GET 就能触发还原 / 装包）。

**等待与性能**
- 「服务启动成功」统一改为等进程 + 等端口应答，上限 120 秒（原来 15 秒，
  而这台机器冷启动实测 28 秒）。
- 状态页进页面不再强制联网刷新版本列表（原来一次加载最多占住 CGI 80 秒）。
- 版本缓存 TTL 真正生效（原来只看文件非空，列表永不过期）。
- 版本号优先读 `package.json`，不再每次轮询都起一个完整 Node 进程。
- `start` 时若顶层属主已正确就跳过 `chown -R`（`$home` 下 7.8G，几十秒）。
- 进程终止改为 TERM → 等 30 秒 → KILL，并确认清空后才删程序目录。

**安全**
- 去掉 `models.sh` 里「SecretRef 失败就明文写 apiKey」的回退：那会把密钥放进
  进程参数。位置参数传 key 也一并拒绝，只保留 `--key-file` 与环境变量。
- rpcd ACL 去掉 `/etc/config/openclaw` 的裸 write 授权（本包写操作都走 cli.sh，
  且该授权能绕过全部路径校验）。

**其它**
- 备份排除规则改为精确路径：原来 `--exclude='logs'` 会匹配任意层级，
  连 `workspace/logs` 这类用户数据一起排除（已实测复现）。
- 日志与诊断命令保留真实退出码：原来 `| tail` 让 `$?` 恒为 0，失败显示成功。
- 备份页的超时不再被无条件覆盖（`x.timeout = 20000` 把 900 秒覆盖掉）。
- 安装日志保留上一份（`.1`），不再每次清空。
- `uci-defaults` 判空改为「键不存在」才写默认值，避免升级重跑时覆盖用户清空的值。
