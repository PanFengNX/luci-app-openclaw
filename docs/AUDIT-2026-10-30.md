## 二、P1 级确认问题

### P1-1：`repair.sh` 普通维修路径绕过 `oc_harden_root_paths()`

**位置**：`root/usr/libexec/openclaw/repair.sh:299-310`

普通 `repair.sh` 路径直接执行：

```sh
chown -R "$OC_USER":"$OC_GROUP" "$BASE"
chmod -R u+rwX "$BASE"
```

这条路径没有调用 `oc_harden_root_paths()`，会重新覆盖上一轮已经收紧的：

- `$BASE/secure/delpass`
- `$BASE/cloud/pass`
- `$BASE/backups`

当安装目录当前属主不是 `openclaw` 时会触发。升级、换盘、手工恢复或权限异常后，用户通常会从 LuCI 执行普通 repair，因此这不是不可达代码。

**影响**：网关进程或第三方插件以 `openclaw` 用户运行时，可读取删除密码哈希、云备份口令和备份归档。

**验证依据**：代码走读已确认 `repair.sh` 不 source 后调用 `oc_fix_perms()`，而是直接递归处理 `$BASE`；`oc_harden_root_paths()` 仅存在于 `lib.sh:1804` 的 `oc_fix_perms()` 路径。

**建议**：统一复用安全权限修复函数，或在 `repair.sh` 递归处理后无条件调用 `oc_harden_root_paths "$BASE"`。增加行为测试：先让 `$BASE` 非 `openclaw` 属主，执行普通 repair，断言三个 root-only 区域仍为 `root:root`、目录 0700、文件 0600。

---

### P1-2：Lua `/tmp/.openclaw` 只拒绝符号链接，不验证 root 属主和父链

**位置**：`luasrc/controller/openclaw.lua:225-235`

`need_dir()` 当前只做：

```lua
if sh("test -L " .. q(RUNDIR) .. " && echo symlink") == "symlink" then
	return false
end
os.execute("mkdir -p " .. q(RUNDIR) .. " && chmod 700 " .. q(RUNDIR))
return true
```

它没有：

- 检查目录属主是否为 root；
- 检查目录是否为真实目录而非其他特殊文件；
- 检查父级路径；
- 处理检查与实际创建/写入之间的 TOCTOU 窗口。

`lib.sh` 的 `oc_rundir()` 已有属主校验，但 Lua 控制器没有复用它，形成两套不一致的临时目录安全模型。

**影响**：如果低权限用户预先创建 `/tmp/.openclaw`，`chmod 700` 会保留该用户属主。LuCI 以 root 写入的临时 API Key、删除密码、云备份口令或授权码可能被该用户读取。目录被替换的竞态也未闭合。

**验证方式**：在隔离设备中由普通用户预创建该目录，再触发 `api_apply`、`api_delpass_set` 或云口令接口，检查临时文件的属主与权限；另做目录替换竞态测试。

**建议**：Lua 侧统一调用经过校验的公共临时目录函数；至少要求目录为 root:root、0700，拒绝符号链接/非目录，并尽量使用安全创建而不是“检查后 mkdir -p”。

---

### P1-3：基础目录/状态目录校验在叶节点不存在且父级为符号链接时可能放行

**位置**：

- `root/usr/libexec/openclaw/lib.sh:1864-1874`
- `root/etc/init.d/openclaw:175-189`

两处逻辑都是只有在完整目标满足 `[ -e "$dir" ]` 时才调用 `readlink -f`。如果最终叶节点不存在，但中间已有目录组件是符号链接，则物理解析被跳过，后续 `mkdir -p` 可能跟随父级符号链接。

示例形态：

```text
/mnt/test/link -> /etc
候选目录：/mnt/test/link/new/OpenClaw
```

候选末端不存在时，字符串校验可能通过；后续创建目录会落入链接目标。

**影响**：基础目录校验的“符号链接目标拒绝”边界不完整，可能将后续创建、权限操作或状态写入导向非预期目录。该问题需要在目标设备上确认 BusyBox `readlink -f` 对不存在叶节点的具体返回，但代码路径缺口已确认。

**建议**：逐级检查所有已存在的路径组件；对“已存在前缀 + 不存在后缀”先解析最长存在前缀，再拒绝前缀物理路径与逻辑路径不一致的情况。`base_dir` 与 `state_dir` 应共用同一实现，避免 shell/Lua/控制器各自复制不完整逻辑。

---

### P1-4：`repair.sh` 不使用自定义 `main.state_dir` 推导维修数据目录

**位置**：`root/usr/libexec/openclaw/repair.sh:103-108`、`136-141`

服务启动使用：

```sh
state_dir="$(oc_state_dir)"
```

但 repair 仍然使用：

```sh
HOME_DIR="$(oc_home_dir)"
DATA="$HOME_DIR/.openclaw"
CONF="$DATA/openclaw.json"
```

当用户配置 `main.state_dir=/mnt/large/openclaw-state` 时，服务和其他部分使用自定义目录，而 repair 检查、创建和修复的是旧的默认目录。

**影响**：真实状态目录损坏时 repair 不能修复；repair 可能修复一个不再使用的旧目录；`owner-fix` 也不能覆盖真正的状态目录。OpenClaw 官方迁移指南明确要求使用同一个 `OPENCLAW_STATE_DIR`，并迁移整个状态目录，否则会出现会话为空、渠道掉线和凭据不可用。

**建议**：`DATA` 与 `CONF` 统一从 `oc_state_dir()` 推导；`HOME_DIR` 只作为 OpenClaw HOME 使用。owner-fix 需要同时处理 `oc_state_dir()` 和其工作区，但必须保留 root-only 区域的权限分类。

---

### P1-5：云备份登录态目录在 `oc_fix_perms()` 后仍可能由服务用户拥有

**位置**：

- `root/usr/libexec/openclaw/cloud.sh:80-85,244-253`
- `root/usr/libexec/openclaw/lib.sh:1755-1788`

云目录包括：

```text
$BASE/cloud
$BASE/cloud/bin
$BASE/cloud/home
$BASE/cloud/pass
```

`cloud_ensure_dirs()` 只设置 0700，不改变属主；`oc_harden_root_paths()` 只处理 `$BASE/cloud/pass`，没有处理 `cloud/`、`cloud/home`、`cloud/bin`。因此 `oc_fix_perms()` 先递归 chown 整个 `$BASE` 后，登录态文件 `$BASE/cloud/home/.config/bdpan/config.json` 仍可能由 `openclaw` 所有，服务用户可读取。

**影响**：网盘登录态或 access token 可能被网关及第三方插件读取。该项与 P1-1 叠加后，普通 repair 也会重新覆盖这些权限。

**官方依据**：OpenClaw 官方迁移指南说明状态目录包含 API Key、OAuth、渠道凭据等机密，要求备份加密并将状态目录权限/所有权正确交给实际运行 Gateway 的用户；本插件自己的 `cloud.sh` 注释又明确将云目录设计为 root 0700，当前实现没有把“root 目录”落实到属主。

**建议**：先明确云组件的运行用户与安装/登录流程，再将登录态目录纳入 root-only 权限模型；如果确实需要服务用户读取，至少拆分可执行组件目录与登录态目录，不能只依赖 0700（因为目录属主仍可能是服务用户）。

## 三、P2 级确认问题

### P2-1：备份解析器对合法文件名仍会跟随符号链接

**位置**：`root/usr/libexec/openclaw/backup.sh:143-180`

`oc_backup_resolve()` 对备份目录中的纯文件名只做：

```sh
[ -f "$d/$in" ] || return 1
printf '%s/%s' "$d" "$in"
```

`[ -f ]` 会跟随符号链接。控制器下载接口已经使用 `lstat` 拒绝链接，但 `backup.sh verify`、`restore` 等入口仍可引用备份目录中的合法文件名链接。

**当前风险判断**：上一轮 P0-2 修复后，正常情况下 `backups` 目录应为 root-only，网关用户不能再创建链接，因此原始攻击链已被削弱；但历史遗留链接、root 侧误放链接或 repair 路径重新放宽权限时仍可触发。应闭合所有入口的 no-follow 规则。

**建议**：`oc_backup_resolve()` 对最终对象做 `lstat`，要求普通文件且不是符号链接；绝对路径分支同样检查。增加 verify/restore 的链接行为测试。

---

### P2-2：`api_run` 仍按首个子命令授权，写操作命令形状过宽

**位置**：`luasrc/controller/openclaw.lua:720-793`

白名单按 `argv[1]` 判断，包含：`mcp`、`devices`、`pairing`、`agent`、`backup`、`system` 等。逐 token 的 `q()` 转义能够防止 shell 结构注入，但不能限制 OpenClaw CLI 的完整子命令形状。

潜在写操作包括：

```text
mcp add ...
devices approve ...
pairing approve ...
agent ...
backup create ...
```

**结论**：不是已确认的 shell 注入，而是命令级最小权限不足。建议用完整命令形状白名单，或把写操作拆成专用、参数严格校验的 API。

---

### P2-3：云组件未收录版本只告警，仍以 root 执行

**位置**：`root/usr/libexec/openclaw/cloud.sh:1148-1164,1540-1582`

哈希白名单只有有限版本。未收录版本进入“告警但继续”分支，之后 `chmod 700` 并由 root 执行安装器。

**风险判断**：需要 CDN、发布源或传输链被污染等前置条件，普通 LuCI 用户不能直接利用；属于供应链加固缺失。

**建议**：默认拒绝未收录版本；若必须支持新版本，应先更新插件内置哈希并发布插件版本。

---

### P2-4：缺少 `timeout` 时，部分超时机制退化为无限执行

**位置**：

- `root/usr/libexec/openclaw/lib.sh:1105-1114`
- `root/usr/libexec/openclaw/install.sh:252-261,720-742`

`lib.sh` 的节点探测与 `install.sh` 的 `run_with_timeout()` 在系统缺少 `timeout` 时直接执行目标程序。项目已有 `oc_timeout()` 的 POSIX/BusyBox 兜底，但这些路径没有统一使用。

**影响**：异常 Node/npm 进程可能长时间占住安装锁、后台任务或 LuCI 请求。

**建议**：统一使用已有 `oc_timeout()`；若确有路径无法使用，应明确实现后台进程、TERM、KILL 和 wait 的兜底，而不是直接执行。

---

### P2-5：core dump 修改全局 `core_pattern`，停止服务不恢复

**位置**：`root/etc/init.d/openclaw:714-735`

开启 `main.core_dumps=1` 时，服务把全局 `/proc/sys/kernel/core_pattern` 改到 OpenClaw 目录，但没有保存旧值，也没有在 `stop_service()` 恢复。其他进程的 core 也会受到影响。

默认关闭降低了暴露概率，但开启排障开关后仍是全局副作用。

**建议**：保存旧值并在停止/关闭开关时恢复；或使用进程级 core 配置，避免改变全局内核设置。

---

### P2-6：`dist-web/index.html` 是过期且不可下载的发布页

**位置**：`dist-web/index.html:31-45`

页面仍宣称：

```text
luci-app-openclaw 1.0.1-r1
luci-app-openclaw-1.0.1-r1.apk
```

但当前版本是 1.8.55，`dist-web/` 中实际只有 1.6.0 资产，不存在页面链接的 1.0.1-r1 包。

**影响**：如果该目录被部署，用户会下载 404 或错误版本；页面还要求先卸载旧版本，与当前覆盖升级兼容规则冲突。

**建议**：更新为当前发布体系，或删除/明确标记为历史预览目录，禁止作为正式发布入口。

## 七、官方依据与审计边界

OpenClaw 官方迁移指南明确要求：

- 迁移必须使用同一个 `OPENCLAW_STATE_DIR` / profile；
- 必须迁移整个状态目录，不能只复制 `openclaw.json`；
- 状态目录包含 API Key、OAuth、渠道凭据等机密；
- 状态目录与工作区的所有权必须与实际运行 Gateway 的用户匹配；
- 备份应加密保存，怀疑泄露时应轮换密钥；
- 迁移后应运行 `openclaw doctor` 并重启、检查状态。

因此本报告把“repair 使用错误 state_dir”和“云登录态权限未形成明确属主模型”列为真实兼容/安全问题，而不是单纯代码风格问题。

## 八、建议修复顺序

1. **P1-1**：先修 `repair.sh` 直接递归 chown 绕过 root-only 加固。
2. **P1-2**：统一 Lua 与 shell 的私有临时目录安全模型，补 root 属主和竞态防护。
3. **P1-3**：逐级解析路径组件，闭合中间符号链接边界。
4. **P1-4**：让 repair 全面使用 `oc_state_dir()`，并补旧数据目录 + 新版本启动验证。
5. **P1-5**：明确云组件运行用户，重新设计 `cloud/bin` 与 `cloud/home` 的权限分层。
6. 再处理 P2-1 至 P2-6，并更新/删除过期 `dist-web` 发布页。

本轮只完成审计与报告，没有应用任何修复补丁。
