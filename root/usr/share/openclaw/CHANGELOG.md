# 更新日志

版本按倒序排列，最新的在最上面。

## 1.8.40

**临时根身份错位：按 Hermes 的实机验证修复。**

### 机制（读 OpenClaw 源码 + 实机验证，不是我猜的）

`resolvePreferredOpenClawTmpDir()` 的解析顺序：

1. 试 `/tmp/openclaw` —— 合格判据两条：属主 == 当前 uid，且 `mode & 0o022 == 0`
2. 不合格 → 回退 `$TMPDIR/openclaw-<uid>`，同样要求属主 == 当前 uid
3. 再不合格 → **硬失败**，一切需要状态的操作被拒

于是现场那个故障的完整链条是：

1. wrapper 给 **root 上下文**设了 `TMPDIR=$BASE/tmp`（VAR 域内）；
2. root 的 fallback 临时根就生在 `$BASE/tmp/openclaw-0` —— **VAR 域内部**；
3. 此后任何一次 `chown -R VAR` 把它翻成服务用户；
4. root 再跑 → `has owner uid 998, expected uid 0` → **永久被拒**。

### 三处修复

**① `/tmp/openclaw` 钉成 `root:root 0700`**（`oc_pin_system_tmp_root`）。

属主与权限位要一起钉 —— 判据含 `mode & 0o022 == 0`，光改属主不够。
放在**服务启动路径**（`procd_open_instance` 之前），因为 `/tmp` 是 tmpfs，
重启即失，只在装包时做一次没用。

钉好之后：root 永远命中 preferred（**不在 VAR 里造目录**），服务用户走自己的
`$TMPDIR/openclaw-<uid>`（落在磁盘，日志因此持久，而不是留在 tmpfs 里重启丢失）。

**② root 上下文不再设 `TMPDIR`**（wrapper）。这是故障的起点，必须断掉。
`TMPDIR=$BASE/tmp` 只允许出现在**以服务用户运行**的命令串里。

**③ 清理判据改为「basename 必须是 `openclaw-<纯数字>`」。**

我 1.8.37 写的清理用的是 `openclaw-*` —— Hermes 实测**误删了 9 个目录**
（`openclaw-update-report-*`、`openclaw-update-run-handoff-*`、
`openclaw-<date>.log` 都在同一层）。

先改成 `openclaw-[0-9]*`，但实测发现它**仍然会命中 `openclaw-2026-10-25.log`**
（日期也以数字开头）。靠 `[ -d ]` 挡掉文件不够 —— 判据要独立成立，
不能依赖"它恰好是文件"。现在用 `oc_is_tmp_root()`：拆出前缀与后缀，
后缀必须非空且全为数字。实测判定：

```
openclaw-0                ✓ 是临时根
openclaw-998              ✓ 是临时根
openclaw-2026-10-25.log   ✗ 不是
openclaw-update-report-x  ✗ 不是
openclaw-                 ✗ 不是
```

### 结构性改动：启动路径不再做 `chown -R`（I4）

这条是「修了反而起不来」的根治。原来启动时会「属主探测 + 条件 `chown -R`」，
两个问题：

- 判据是 **root 视角**（`stat -c %U`）。root 对被 root 拥有的 0755 目录永远可写，
  所以这类判据只能看出「属主名字不对」，看不出「**服务用户实际打不开**」。
- 判据只看**顶层**属主。内部被 root 写过的文件（doctor 以 root 跑就会产生）
  不会被发现；一旦发现就退回全树 `chown -R` —— 7~8G、几万文件、几十秒，
  还可能与正在运行中的网关抢同一批文件。

现在启动只做 O(1) 断言，并以**服务用户身份**跑真实写入探针；
失败就 fail closed（不启动），并打印一条可直接复制的修复命令。
真正的属主修正只发生在显式维护路径：**`repair.sh owner-fix`**（新增）。

### 顺带

- `core_pattern` 从 `$base/logs`（VAR 域）改到 `$base/dumps`（DIAG 域，
  `root:root 0700`）：core 的属主取决于崩溃进程，留在用户域里会制造
  「非服务用户属主的文件」，清理还得动用户域。
- 启动日志固定打印 `user=... base=... state=... tmp_root=...`，现场一眼可查。
- 安装收尾以服务用户身份自检，失败即判安装失败 —— 与其「装完了但网关起不来」，
  不如装不上并说清原因。
- `oc_as_user` 的命令串内补 `cd $HOME`：root 从 `/root`（0700）调用时，
  su 之后 cwd 仍是 `/root`，子进程 chdir 失败，只报一句与权限无关的
  `Command failed during launch or output capture (EACCES)`。

## 1.8.38

**chown 那条告警：我上一轮的归因是错的，这次改成能查到原因。**

上一轮我把「无法把 /SSD/OpenClaw/home 的属主改为 openclaw」归因为
"exfat/ntfs 不支持属主"。但同一份日志里，OpenClaw 报的是
`has owner uid 998, expected uid 0` —— **它能读出 uid 998**，说明该分区
完全支持属主，不是 exfat/ntfs。归因错了。

真正的问题是我们把报错丢掉了：`chown -R ... 2>/dev/null || _warn_chown`，
只留一句"失败了"，永远查不出为什么。现在 `_warn_chown` 会重新执行一次并
**带出第一条真实报错**，例如只读挂载、inode 用尽、某个子目录不可改。
（exfat/ntfs 上仍按文件系统能力降为说明性提示，那种情况确实无从修复。）

要判断是"OpenClaw 要这么高权限"还是"设置问题"，答案是：**都不是。**
`openclaw` 这个专用用户是**本插件**主动选择的（`procd_set_param user`），
不是 OpenClaw 的要求；属主修正也是本插件做的。所以这条告警反映的是
"我们改不了这个目录的属主"，而不是"OpenClaw 权限太高"或"你配错了"。

**备份范围文案与实际不符（你截图里那句）。**

确认框写「配置 + 会话 + 工作区」，但归档实际还有**插件清单**与
**定时任务**两样（1.8.34 加的）。文案不改的话，用户会以为恢复后插件也在里面 ——
而插件装在程序目录、不在备份内，只能记清单。现在确认框写明：

```
本次备份范围：配置 + 会话 + 工作区
另外还会记录：插件清单、定时任务（备份计划）
不包含：日志、缓存、node_modules
注意：插件本体装在程序目录，不在备份内。恢复后需按清单重装。
```

实测确认归档确实包含 `plugins.txt` / `crontab.txt` / `sessions` / `workspace`。

**关于 `openclaw-watchdog` 的 cron.err：**

`crond[13218]: USER root pid 7797 cmd /usr/bin/openclaw-watchdog` —— 这个
二进制**不是本插件安装的**（本插件只装 `/usr/bin/openclaw` 一个）。它来自
别处（旧脚本或手工放置），属于 `cron.err` 级别的执行失败。本插件不接管它；
若要清理，请确认来源后自行删除对应的 crontab 行与文件。

## 1.8.37

**升级成功了（2026.10.6 → 2026.10.7，服务已起来），但日志暴露三处遗留问题。**

### 1. `doctor` / `gateway status` / 插件安装都被拒

日志里：

```
Unsafe fallback OpenClaw temp dir "/SSD/OpenClaw/home/.cache/openclaw-0";
has owner uid 998, expected uid 0
Doctor could not enter maintenance. failed to acquire gateway state ownership
```

根因是**执行身份不一致**：所有 OpenClaw CLI 都以 **root** 运行，而网关以
**uid 998** 运行。OpenClaw 的临时目录名是 `openclaw-<uid>`，并且会
**校验它属于当前进程的 uid**（防符号链接 / 共享临时目录攻击）。于是：

1. root 跑 → 建出 `openclaw-0`；
2. 我们的 `oc_fix_perms` 又 `chown -R` 把整个 home 改成 998；
3. 下次 root 再跑 → 看到"自己的临时目录属于 998" → 拒绝一切需要状态的操作。

修法两步：
- 新增 `oc_as_user()`，`doctor` / `config validate` / `gateway status --deep` /
  插件安装全部**以网关用户执行**，uid 自始至终一致；
- 升级前清掉历史遗留的 `openclaw-<uid>` 缓存目录（它只是缓存，重建无害）——
  已经落在设备上的 `openclaw-0` 靠这一步清掉，不然修了代码也仍然报错。

### 2. 插件安装失败的原因被藏起来了

日志只有一句 `OpenClaw config is invalid`，然后 `WARN: DeepSeek 插件安装失败`。
真正的键是 `channels.qqbot: unknown channel id: qqbot` 与
`agents.defaults.heartbeat.target: unknown heartbeat target: qqbot` ——
**旧版残留的通道配置**（不是本插件写的），2026.10 已不认这个通道 id。
现在 `doctor` 之后会跑 `openclaw config validate`，把**具体哪个键无效**
写进安装日志，并给出处理建议。

### 3. `WARN: 未找到 timeout 命令`

这条只是提示。本机 busybox 没有 `timeout`，`install.sh` 里已用
`run_with_timeout` 兜底（exec 了 GNU timeout，不存在时退化为不设上限）。

## 1.8.36

**升级失败的真因：`--prefer-offline` 让 npm 用旧缓存。**

日志里 `npm error notarget No matching version found for openclaw@2026.10.7`
看起来像"这个版本不存在"。实际查证：`registry.npmjs.org` 与
`registry.npmmirror.com` **都有** 2026.10.7，而且它就是 `latest`。
真正的原因是 npm 那次请求只用了 101ms 且标着 `cache stale` ——
我们传了 `--prefer-offline`，它让 npm 直接采信本地缓存里的旧版本列表，
于是"版本列表说有、npm 说没有"。改为 `--prefer-online`。

顺带去掉 `npm_config_tmp`：npm 11+ 已移除该配置项，只会刷
`npm warn Unknown env config "tmp"`，对行为没有影响。临时目录改用 `TMPDIR`。

**「能查到更新的是哪个源，能否用那个」——可以，现在就是这么做的。**

原来只记录 `official|mirror`，安装阶段要重新按 `main.npm_registry` 推断地址；
推断结果一旦与取列表时不同，就会出现上面那种"列表有、安装没有"。
现在把**实际成功的完整 registry URL** 落盘（`oc-source-url.txt`），
安装时优先复用它；只有没有记录时才用配置值。

**「已安装的不要重装」——OpenClaw 也加了跳过。**

Node 一直有跳过，OpenClaw 没有：每次点升级都重新 `npm install` 一遍，
即使版本完全相同。现在先问程序自己 `--version`，与目标一致就直接返回。
（注意判定放在**停服务之前** —— 否则跳过时网关已被停掉却不会重启，
等于"点了一次升级，服务挂了"。）

**所有日志都能复制 / 导出。**

统一了一套 `ocCopyText` / `ocDownloadText` / `ocBindLogTools`：
- 复制必须带 `execCommand` 退路 —— `navigator.clipboard` 只在 https / localhost
  可用，而用户访问的是 `http://192.168.x.x`，主路径在路由器上永远走不通。
- 导出生成 `.txt`，文件名带时间戳，避免多次导出互相覆盖；不支持 Blob 的
  老浏览器退回新窗口显示全文。
- 覆盖：日志页、渠道页、命令行页、云端备份输出、状态页诊断输出、
  升级弹窗、安装日志弹窗。

**`chown` 失败告警：在 exfat/ntfs 上是必然的，不该报成故障。**

日志里那条「无法把 /SSD/OpenClaw/home 的属主改为 openclaw」来自 `chown -R`。
但 exfat / vfat / ntfs 没有真正的 uid/gid 语义，`chown` 必然失败 ——
而这几个文件系统正是 USB 硬盘/SSD 上最常见的，本插件也允许把数据装到上面。
用户看到告警却做不了任何事。现在先判断文件系统能力（以 `/proc/mounts` 为准，
因为 `stat -f -c %T` 在部分环境返回 `UNKNOWN`），不支持就跳过 `chown`，
只修权限位，并把提示改成说明性的。

## 1.8.35

**「无法升级」的根因，以及按官方文档补齐升级流程。**

### 根因：陈旧锁永久挡住升级

`install-bg` 用的是裸 `oc_locked()` —— 它只判断**锁目录是否存在**。
于是任何一次被 SIGKILL、OOM、断电打断的操作都会把目录留在那里，
此后**每一次升级都被"另一个操作正在运行"拒绝**，用户除非知道要
`cli.sh unlock`，否则再也没有升级入口。

改为 `oc_lock_busy()`（问"有没有**活着的**进程持锁"）。陈旧锁交给
`install.sh` 里的 `oc_lock_acquire` 原子接管 —— 那里本来就有完整的
陈旧判定和 `mv` 抢占，只是升级入口绕过了它。

### 顺带：借鉴 iStore，升级入口自己清理残留

升级入口不该假设"上一次是干净结束的"。现在 `install-bg` 启动前会：
清掉陈旧锁、清掉上一次的完成标记 / rc / pid / start / logpath、
把上一次的日志移成 `.1`（**不删**，那是失败的唯一现场）。
剩下真正在跑的 `install.sh` 由 `oc_inst_alive` 拒绝 —— 这个拒绝是对的。

### 按官方文档补齐三处（此前都没有）

查了 `docs.openclaw.ai/install` 与 `install/updating`，我们缺三步：

1. **`--allow-scripts=openclaw`**。npm 12 默认**阻止**未批准的 package
   lifecycle scripts，而 OpenClaw 的 `preinstall` / `postinstall` 正是这类；
   不显式批准会被 blocked，表现为"装完了但跑不起来"。
   但 npm ≤11.15 没有这个选项、带了会直接报错，所以按版本探测：
   `>=12` 必加、`11.16+` 也加、`<=11.15` 绝不加。
2. **`openclaw doctor --fix`**。官方安装器在升级已有安装后必跑
   （`--non-interactive`，best effort）。不跑的后果很具体：`openclaw.json`
   的 schema 随版本演进，不修的话升级完可能起不来或功能异常，日志里只有一句
   `config invalid`。已插入为独立阶段（阶段总数 7→8）。
3. **`sharp` 的 `SHARP_IGNORE_GLOBAL_LIBVIPS=1`**。官方安装器默认设，
   避免它在路由器上尝试对系统 libvips 做原生构建（必然失败或极慢）。

另外补了官方升级序列的最后一步 **`openclaw gateway status --deep`**：
端口通只说明进程在听，不说明网关自己认为健康（插件加载失败、schema 未迁移完
都可能仍然监听）。结论记进安装日志。

### 拒绝也要留痕

`install-bg` 的三条拒绝路径（base_dir 不安全 / 有锁 / 已有安装进程）此前
只写 stderr 就 `exit 2`，**不创建也不写日志**。于是面板打开"升级日志"只能
显示"暂无安装日志"，用户完全不知道被拒的原因。现在拒绝也写一行进安装日志。

## 1.8.34

**安装日志路径现在三个进程口径一致。**

`install.sh` 在 `/var/log` 不可写时会回退到 rundir，但那是**它自己进程内的
变量**。`cli.sh` 是另一个进程，`install-status` 报告给面板的仍是
`/var/log/...` 那个写不进去的路径 —— 于是面板永远显示空日志，而真正的日志
在别处。现在 `install.sh` 把实际使用的路径写到 `install.logpath` 标记文件，
`install-status` 读它，`api_ilog` 再跟 `install-status`。
（这个缺口是"改了回退、没改报告"造成的，和前面那个 `.1` 问题是同一类。）

## 1.8.33

**让 OpenClaw agent 能自己看日志（问的是这件事）。**

先分清两件事：**不能**让 agent 改插件代码，**能**让它读日志。

- 改代码不行：包内文件是 `root:root`，网关以 `uid=998` 运行，没有写权限。给它
  权限就等于让网关能改 LuCI 控制器，而 LuCI 以 root 执行 —— 一条直接的提权链。
- 读日志可行，而且现在是设计的一部分：把快照写进**网关自己的数据目录**
  （`<state_dir>/diagnostics/`），那个目录本来就属于网关用户，agent 天生能读。
  **不需要新权限，也不需要开端口。**

新增两个命令与一个按钮：

- `cli.sh snapshot [lines]` —— 只读、不落盘，stdout 一个 JSON：
  `status`（是否运行 / 端口是否应答）、`paths`、`logs`（网关与系统日志尾部）、
  `crash`（dmesg 与 core_pattern）。
- `cli.sh diag-export [--out DIR] [--lines N]` —— 落盘到 `diagnostics/`：
  `snapshot.json`、`gateway-log-tail.txt`（真正有崩溃堆栈的那份）、
  `manager-log-tail.txt`、`crash.txt`，外加一份 `README.txt` 告诉 agent
  按什么顺序读。写完把属主改成网关用户，否则它读不到。
- 「日志」页新增「生成给 OpenClaw 的诊断快照」按钮。

说明见 `docs/AGENT-DIAGNOSTICS.md`。`diagnostics/` 已从备份排除（可重建的
诊断产物，进归档只会让备份变大）。

**顺带修掉截图里的问题**

截图里弹窗写着"进行中"，页面底部却写"异常中断"，日志还是空的 —— 三处叠加：

- `api_ilog` **硬编码**读 `/var/log/openclaw-install.log`。而 `install.sh`
  每次启动都先把上一轮日志 `mv` 成 `.1` 再清空主文件；如果本轮刚启动就退出，
  主文件是空的，**有用内容全在 `.1` 里**，界面却从不读它。现在跟随
  `install-status` 返回的真实路径（`/var/log` 不可写时它会回退到 rundir），
  并在主日志为空时回退读 `.1`，都空则把查找过的路径打出来。
- `upModalOpen()` 无条件把状态设成"进行中"，所以「查看升级日志」打开历史

## 1.8.31

**修复 1.8.28~1.8.30 一直存在的致命错误：所有接口 500。**

1.8.28 我把 57 个端点从 `call("api_xxx")` 改成了
`call(guarded("xxx", api_xxx))`，想用一层包住来加 POST 校验。但 LuCI 的
`call()` **只接受字符串函数名**：

```lua
local function _call(self, ...)
    local func = getfenv()[self.name]     -- 按名字查环境
    assert(func ~= nil, 'Cannot resolve function "' .. self.name ..
           '". Is it misspelled or local?')
```

传函数对象进去，`getfenv()[函数]` 得到 `nil`，assert 直接抛异常 ——
**每一个 API 请求都 500**。而页面模板不走 `call()`，所以界面能正常渲染，
只是所有数据都读不到：挂载点空、程序位置永远「读取中…」、版本列表
「服务无响应」、模型下拉空、网盘状态失败。

1.8.29 我修的是同一个函数的另一个独立缺陷（`out` 的前向引用），
没有触到这条，所以症状照旧 —— 这次用真实 Lua 5.1 把每条路由跑了一遍才定位到。

修法：注册改回 `call("api_xxx")`；POST 校验改为在文件末尾把包环境里的
`api_*` 统一换成守卫版（`getfenv(1)[name] = guarded(name, fn)`）。
集中式校验保留了，但不再试图把函数对象塞给 `call()`。

新增两项回归（都接进 `verify-project.sh`）：

- `tools/tests/lua-dispatch.py` — 静态检查，`call()` 的参数必须是字符串字面量，
  且不能指向文件局部函数（`getfenv()` 看不到局部函数）。
- `tools/tests/lua-dispatch-run.py` — 用真实 Lua 5.1（`lupa`）加载控制器，
  模拟 LuCI 的 `module`/`entry`/`call`/`_call`/`setfenv`，把 **57 条 API 路由
  逐条 dispatch 两次（GET + POST）**，任何一条抛异常即失败。

对照验证：修复前 57 条全部失败，修复后 57 条全部通过。

这类错误的共同点值得记住：**语法合法、单元测试通过、页面能渲染，只有真正
调度一次才会暴露。** 所以这次不是再改一遍代码，而是补上了能跑的验证。

- 未安装 / 已停止时不再探测网关端口（原来每次白等 1-3 秒，结论无意义）。
- 「端口未应答」的提示此前被 `renderOpen()` 覆盖、永远看不到；现在提示只有一个来源，
  按「端口无效 > 端口未应答 > 服务未启动」的优先级显示。

  改为 `.oc-row>` 子选择器，不依赖 Selectors Level 4。
- `collectEnvPayload()` 返回值改为结构体，不再往表单数据里塞 `__install` / `__nm`
  再让调用方 `delete`（漏删会把 `[object Object]` 发给服务端）。
- `install.sh` 把 xz 当硬前提（缺了直接给出 `opkg install xz-utils` 提示），
  不再只 warn 然后以「解压失败（tar）」收场；`repair.sh` 也一并检查 xz。
