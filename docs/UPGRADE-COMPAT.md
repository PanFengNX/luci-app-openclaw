# 升级与向后兼容（设计规范）

本文件是**约束**，不是建议。任何改动数据目录、文件名、配置键、cron 行、进程
布局的提交，都必须按这里的规则走。做不到就在 PR/提交说明里写明为什么，并给出
替代方案 —— 不允许"先改了再说"。

---

## 为什么要有这份规范

这个项目已经踩过两次同类问题，都是"代码本身没错，但升级路径断了"：

| 变更 | 如果没处理会怎样 |
| --- | --- |
| crontab 备份从 `/etc/crontabs/root.openclaw.bak` 移到插件私有目录 | 老设备上那份备份留在 crontab 目录里，busybox crond 会把它当成一个用户名去加载，轻则刷 syslog，重则备份每天跑两遍 |
| 定时任务命令从写死绝对路径改为可回退 | 非标准安装位置上，crontab 里的旧行指向不存在的脚本，cron 静默失败 —— 用户以为在备份，实际一份都没有 |

共同点：**旧版本留在设备上的东西，新版本没有接管**。用户升级时不会重装数据盘、
不会手改 crontab、不会读你的 CHANGELOG。升级路径必须自己处理。

---

## 规则

### 1. 数据目录与文件名是公开契约

`<安装目录>/home`、`<安装目录>/openclaw`、`<安装目录>/cloud`、`/etc/config/openclaw`
里的键名、`/var/log/openclaw*.log` 的路径 —— 这些都算对外契约。改名/移动属于
**破坏性变更**，必须同时提供迁移，不能只在 CHANGELOG 里写一句"路径变了"。

### 2. 迁移必须幂等、可重入

同一份迁移在任意时刻被跑第二次、第三次，结果必须与第一次相同。设备可能在迁移
中途断电，下次启动会再跑一遍。

判断"是否已迁移"要靠**状态**（旧路径不存在 / 新路径已存在 / `config_version`
已达标），不要靠"这次是升级安装"这种外部信息 —— `postinst` 在重装时也会跑。

### 3. 先复制、再验证、最后切换；失败不能毁掉原数据

```
旧位置 --copy--> 新位置 --verify--> 切换引用 --成功后才清理旧位置
```

任何一步失败都**保留旧位置不动**，并让用户在日志里看到。绝不允许"先删旧的再写新的"。

### 4. 新配置项必须有代码侧默认值

新增 UCI 键时，所有读取处都要写成 `uci_get main.xxx <默认值>`。这样**老配置
（没有这个键）无需任何迁移就能跑**，`uci-defaults` 只是把默认值写进文件、
让用户看得见，不是运行前提。

反例：如果读的时候写成 `uci_get main.xxx ''` 再自己判断空值，老配置会走进
一个"没配置"的分支，行为与新版不一致 —— 这属于隐式破坏兼容。

### 5. 删除文件/功能要给显式 legacy 清单

清理旧版本遗留物时，**逐条列出确切路径**，不要用通配符扫目录：

```sh
# 对：只删这一个我们曾经写过的文件
[ -f "$OC_CRONTAB.openclaw.bak" ] && rm -f "$OC_CRONTAB.openclaw.bak"

# 错：会把用户自己放在这里的同名文件一起删掉
rm -f /etc/crontabs/*.bak
```

### 6. 升级后要能"读旧写新"

新版本至少要能**读得懂旧版本写下的数据**（配置、备份归档、状态文件）。
只有在旧格式确实无法表达新语义时才做格式迁移，且迁移要有版本号。

### 7. 降级也要想一次

用户装回旧版本时会发生什么？如果新版本已经写过旧版本不认识的键/文件，
旧版本会不会崩？至少要保证**旧版本忽略新键后仍能启动**（这也是规则 4 的理由）。

## 怎么做：迁移的标准形状

### 配置文件版本号

> 现状（1.8.4）：`main.config_version` **尚未引入**。第一次真正需要迁移用户数据时
> 按下面的配方引入即可。已有的 crontab 遗留清理是幂等的、在每次写 cron 时执行，
> 不需要版本号 —— 判断"要不要迁移"靠的是**旧文件在不在**，而不是"这次是不是升级"。

`/etc/config/openclaw` 的 `main` 段维护 `config_version`（整数）。每次需要迁移
就 +1，并在 `root/etc/uci-defaults/99-openclaw` 里按顺序补齐：

```sh
# uci-defaults 里，按版本号顺序执行，每步都幂等
cur="$(uci -q get openclaw.main.config_version)"; cur="${cur:-0}"

if [ "$cur" -lt 1 ]; then
    # v1：crontab 备份从 /etc/crontabs 移到插件私有目录
    #     （2026-10 的 1.8.4 做过；旧文件必须清掉，否则 crond 会误加载）
    legacy="/etc/crontabs/root.openclaw.bak"
    [ -f "$legacy" ] && rm -f "$legacy"
    uci -q set openclaw.main.config_version=1
fi

if [ "$cur" -lt 2 ]; then
    # v2：示例 —— 未来某个真实的迁移
    :
    uci -q set openclaw.main.config_version=2
fi

uci -q commit openclaw
```

要点：
- `cur` 从 UCI 读，读不到按 0（老设备）；
- 每步只做一件事，只判断 `cur < N`，**不看"是不是升级"**；
- 每步自己保证幂等（文件不存在就跳过）；
- 全部跑完后才 `commit`，避免中途断电留下半套。

### 移动一个目录

```sh
old="$base/old-name"; new="$base/new-name"
if [ -d "$old" ] && [ ! -e "$new" ]; then
    # 1) 先复制到临时名，避免半成品被当成新目录
    cp -a "$old" "$new.tmp" || { warn "迁移失败，保留旧目录"; return 1; }
    # 2) 验证（条目数一致是最低要求；关键数据再比对内容）
    [ "$(ls -A "$old" | wc -l)" = "$(ls -A "$new.tmp" | wc -l)" ] || {
        warn "迁移校验失败，保留旧目录"; rm -rf "$new.tmp"; return 1; }
    # 3) 原子切换
    mv "$new.tmp" "$new"
    # 4) 旧目录先改名保留，不直接删 —— 用户回滚时还有救
    mv "$old" "$old.migrated-$(date +%Y%m%d)"
fi
```

`$old.migrated-*` 由用户在确认无误后自行删除，或在**下一个大版本**里清理
（清理时同样要列进 legacy 清单）。

## 发版前检查清单

改动了下面任意一项时，逐条回答：

- [ ] **数据目录 / 文件名**变了？→ 有没有迁移？旧路径还在的设备上会发生什么？
- [ ] **UCI 键**改名或删除？→ 读取处是否都有默认值？旧键要不要读一次并写回新键？
- [ ] **cron 行**变了？→ 旧行会不会残留？旧行指向的脚本还存在吗？
- [ ] **进程/服务**布局变了（unit 名、用户、端口）？→ 升级时旧进程会被停掉吗？
- [ ] **归档格式**变了？→ 旧归档还能恢复吗？新归档被旧版本读会怎样？
- [ ] 迁移是否**幂等**？断电重跑会怎样？
- [ ] 迁移失败时**旧数据是否完好**？日志里能看到原因吗？
- [ ] 用**上一版的数据目录**启动新版，跑一遍完整回归了吗？

最后一条是硬要求：`tools/verify-project.sh` 跑的是"干净安装"，它不会发现
升级路径的问题。改动了上述任意一项时，要手工做一次"旧数据 + 新版本"的启动验证，
并在提交说明里写明结果。

## 先例（照这个来）

- `root/etc/uci-defaults/99-openclaw`：创建服务用户、初始化目录、写默认键 ——
  每一步都先判断再动手，重装不报错。
- `cloud.sh` 的 `cloud_cron_legacy_cleanup`：删除旧版本写在 `/etc/crontabs/` 下的
  备份，只删确切的一个文件名。
- `cmd_migrate`（`istorec/openclaw.sh`）：把已有的 OpenClaw 安装复制进本插件目录，
  先复制到暂存区、验证后再原子换入，源目录始终不动 —— 这是"规则 3"的完整实现。
- `main.state_dir` / `main.openclaw_dir`：允许指向 `base_dir` 之外，`info` 与
  网关读同一份推导逻辑（`oc_state_dir`），避免"UI 写一个目录、网关读另一个"。
