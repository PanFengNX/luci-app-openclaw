## 一、结论摘要

共确认 **9 项缺陷**：

| 级别 | 数量 | 含义 |
| --- | --- | --- |
| P0 | 2 | 功能静默失效 / 敏感凭据权限越界，必须在下一个版本修 |
| P1 | 3 | 安全边界可绕过或校验器未接线，应尽快修 |
| P2 | 4 | 加固项，可在后续版本处理 |

**没有发现可直接远程利用的未授权执行漏洞。** 所有安全项都需要「已登录 LuCI 管理员」
或「网关进程（openclaw 用户）已被攻陷」作为前置条件，属于纵深防御层面的缺陷。

最值得优先处理的是 P0-1：**备份恢复时定时任务与插件清单的恢复逻辑从未执行过**。
这不是安全问题是功能问题，但后果是「用户以为恢复成功，实际自动备份静默消失」，
正是 `docs/UPGRADE-COMPAT.md` 里记录过两次的那类事故。

## 二、P0 级（必须修）

### P0-1 备份恢复：暂存目录先被删除，定时任务与插件清单永远不恢复

**位置**

- `root/usr/libexec/openclaw/backup.sh:707` — `rm -rf "$stage"`
- `root/usr/libexec/openclaw/backup.sh:713` — `if [ -s "$stage/crontab.txt" ]`
- `root/usr/libexec/openclaw/backup.sh:739` — `if [ -s "$stage/plugins.txt" ]`

**证据（实测）**

```text
$ grep -n 'rm -rf "\$stage"' backup.sh
707:	rm -rf "$stage"
$ grep -n 'stage/crontab.txt\|stage/plugins.txt' backup.sh
713:	if [ -s "$stage/crontab.txt" ]; then
739:	if [ -s "$stage/plugins.txt" ]; then
```

第 707 行在数据目录恢复完成后立即删除整个暂存目录，第 713 / 739 行随后才去读
该目录下的两个清单文件。目录已不存在，`-s` 恒为假，两个分支**永远不进入**。

而清单是在备份阶段写入的（440 行 `plugins.txt`、446/448 行 `crontab.txt`），
备份侧完好，**只有恢复侧断了**。

**引入历史（git 追溯）**

```text
$ git log --oneline -S 'stage/crontab.txt' -- backup.sh
a0496cf feat(ui): ... complete backups        # 恢复逻辑在这里加入
$ git log --oneline -S 'rm -rf "$stage"' -- backup.sh
13a6073 fix: ... restore safety               # 删除动作更早就在这里
```

`13a6073`（第 115 个提交）先把 `rm -rf "$stage"` 放在数据恢复之后；
`a0496cf`（第 118 个提交）才加入 crontab / plugins 的恢复逻辑，**直接加在了删除动作
之后**。也就是说这个功能**从诞生起就没有执行过一次**，从未被验证。

**影响**

- 恢复备份后，`# openclaw` 标记的定时备份任务不会写回 crontab → 用户以为恢复了，
  实际云备份从此静默停止
- 备份里记录的插件清单不会提示 → 用户重装后某个 provider 莫名不可用，直到自己发现

**建议**

把 `rm -rf "$stage"` 移到 6b / 6c 两个段落之后；或在删除前把两个清单复制到独立的
私有临时文件。必须补回归断言：构造含 `crontab.txt` / `plugins.txt` 的备份，恢复后
断言 crontab 中 `# openclaw` 行存在、且插件清单产生了告警输出。

### P0-2 `oc_fix_perms()` 递归接管整个安装目录，把 root-only 凭据交给服务用户

**位置**

- `root/usr/libexec/openclaw/lib.sh:1755-1765` — 对 `$base` 做 `chown -R` + `chmod -R`
- 敏感文件定义：`lib.sh:1304-1305`（`$(oc_base_dir)/secure/delpass`）、
  `cloud.sh:81-83`（`$(oc_base_dir)/cloud/pass`）
- 调用点：`models.sh:1014`、`channels.sh:395`、`backup.sh:749`、`backup.sh:788`

**证据**

```sh
if [ -d "$base" ]; then
    if grep -q "^${OC_USER}:" /etc/passwd 2>/dev/null; then
        chown -R "$OC_USER":"$OC_GROUP" "$base" 2>/dev/null || ...
    fi
    chmod -R u+rwX "$base" 2>/dev/null
fi
```

两个敏感文件都在 `$base` 之下：

```sh
oc_delpass_dir()  { printf '%s/secure' "$(oc_base_dir)"; }      # lib.sh:1304
OC_CLOUD_PASS="$OC_CLOUD_ROOT/pass"                             # cloud.sh:83
OC_CLOUD_ROOT="$(oc_base_dir)/cloud"                            # cloud.sh:81
```

而 `lib.sh:1300` 的设计注释明确写着这两个文件应为 **root 属主、0600**：

```text
# 存储：$(oc_base_dir)/secure/delpass，目录 0700、文件 0600、root 属主。
```

实现与设计意图直接冲突：一次 `oc_fix_perms` 就把 `secure/delpass`（删除密码哈希）
和 `cloud/pass`（云备份加密口令）改成 `openclaw` 属主，网关进程可读。

**触发条件**：任何一次模型配置保存、渠道配置、备份恢复、安装流程。

**影响**：网关或任一第三方 OpenClaw 插件被攻陷后，攻击者可直接读取云备份加密口令，
进而解密用户上传到网盘的备份内容。这是从「网关失陷」升级到「备份数据全泄」的跳板。

**建议**

不要对 `$base` 做整体递归。按用途拆开：

| 目录 | 属主 | 权限 |
| --- | --- | --- |
| `$base/home`、`$base/workspace`、`$base/tmp`、`$base/logs` | `openclaw` | 递归可写 |
| `$base/secure`、`$base/cloud/pass` | `root` | 0700 / 0600 |
| `$base/backups` | `root` | 0700（见 P1-2） |

修复后加断言：`stat -c %U $base/secure/delpass` 必须是 `root`。

## 三、P1 级

### P1-1 改删除密码时，状态查询失败会 fail-open（跳过旧密码校验）

**位置**：`luasrc/controller/openclaw.lua:1728-1738`

```lua
local raw = sh(SH .. " delpass-status")
if raw:find('"set":true') then
    local old = http.formvalue("old") or ""
    local okold, oerr = delpass_gate(old)
    if not okold then ... return end
end
cloud_reply(cli_exec_stdin("delpass-set", pass .. "\n"))
```

`sh()` 的实现（`openclaw.lua:190-195`）是 `util.trim(sys.exec(args))` —— **只取 stdout，
丢弃退出码**。所以只要 `delpass-status` 因为权限、路径、执行失败、输出格式变化等原因
返回空或异常文本，`raw:find('"set":true')` 为假，就直接跳过旧密码校验并写入新密码。

**影响**：删除密码的设计目的就是「防止拿到页面的人删数据」。后端一抖动，这层保护
就整体失效，且**没有任何日志表明这次绕过了校验**。

**建议**：改用能拿到退出码的执行方式，只有明确解析出 `{"ok":true,"set":false}` 时才
允许无旧密码设置；空输出、非零退出码、解析失败一律 fail-closed 拒绝。不要用字符串
`find()` 判断状态，解析成结构再判。

### P1-2 备份下载跟随符号链接，与 P0-2 组合成任意文件读取

**位置**：`luasrc/controller/openclaw.lua:1263`（`io.open(dir .. "/" .. f, "rb")`）

文件名已由 `SAFE_NAME` 限死（不含 `/`），目录也校验了绝对路径且不含 `..`，
**但没有任何 lstat / 普通文件检查**。备份目录是 `$(oc_base_dir)/backups`
（`backup.sh:39`），位于 `$base` 之下 —— 正好被 P0-2 的递归 chown 交给了 `openclaw`。

**攻击链**：网关用户被攻陷 → 在备份目录创建 `合法名.tar.gz -> /etc/shadow` →
管理员点「下载」→ LuCI 以 root 跟随链接读出目标文件。

**建议**：备份目录保持 `root:root 0700`，不被服务用户写入；下载前 `lstat` 确认是普通
文件；更严格的做法是 no-follow 打开并在打开后复核真实路径仍在备份目录内。
`backup.sh` 的 `oc_backup_resolve()` 也应拒绝最终对象是符号链接。

### P1-3 `_state_dir_safe()` 是死代码，`main.state_dir` 实际无校验

**位置**：`root/etc/init.d/openclaw:151`（定义）、`:440`（使用）、`:539`（`mkdir -p`）

```text
$ grep -n '_state_dir_safe' root/etc/init.d/openclaw root/usr/libexec/openclaw/*.sh
root/etc/init.d/openclaw:118:	# 纯字符串过滤，不碰文件系统。_state_dir_safe() 会对「原路径」和
root/etc/init.d/openclaw:151:_state_dir_safe() {
```

**除定义与注释外没有任何调用点。** 而 `oc_state_dir()`（`:100-113` 与
`lib.sh:258-273` 各一份）只做「读 UCI + 去尾斜杠」，没有形态过滤。
`start_service()` 直接 `state_dir="$(oc_state_dir)"` 后 `mkdir -p "$state_dir/workspace"`、
`oc_schema_heal` 写入。

**影响**：`main.state_dir=/etc`（手工 uci set、旧配置遗留、迁移脚本出错）会把
`/etc/workspace` 建出来、把 `openclaw.json` 写到 `/etc`，污染系统目录。

**建议**：把校验集中到 `lib.sh` 一份，`oc_state_dir()` 的调用方在创建/写入/递归权限
操作前必须 fail-closed 校验；init.d 里那份重复实现删掉，避免再次出现「改了但没接线」。
补测试：`/etc`、`/mnt/x/../etc`、指向 `/etc` 的符号链接都必须被拒。

## 四、P2 级（加固项）

### P2-1 云组件安装器：未收录版本只告警不拒绝，随后以 root 执行

`cloud.sh:1157-1172` 的 sha256 白名单只有 `3.7.3` / `3.7.1` 两个版本的 arm64/amd64。
未命中时走 `else` 分支：只 `oc_warn` 记录 sha256，然后 `chmod 700` 并执行。

代码注释已明确承认「只记录哈希没有任何防护作用」，这是**有意识的取舍**，不是疏漏。
但安全上应改为默认拒绝：`main.bdpan_version` 与 `cli-update <ver>` 都是用户可指定值
（`cloud.sh:1712`、`2019-2026`），只有 `cloud_version_valid` 的字符集/长度检查。

**评级说明**：本条与独立审查的「高危」评级不同。理由是它不可被本地用户直接利用 ——
要成立必须能劫持 CDN 或污染官方发版，属于既有威胁模型内的供应链加固缺失。
建议：未收录哈希直接拒绝安装，并在页面提示「该版本尚未收录，请先更新插件」。

### P2-2 `api_run` 命令白名单按首个子命令放行

`openclaw.lua:701-770` 白名单含 `mcp` / `devices` / `pairing` / `agent` / `backup` /
`system`。逐 token 单引号转义能阻止 shell 结构注入（这一点是对的），但命令级最小权限
不足：`devices approve`、`pairing approve`、`mcp` 的增删配置都会被执行。

建议从「允许首个子命令」改为「允许完整命令形状」，对写操作子命令拆成专用 API。

### P2-3 启用 core dump 会改写全局 `core_pattern`

`init.d/openclaw:699-720` 把 `/proc/sys/kernel/core_pattern` 改成 `$base/dumps`。
这是全系统生效的内核设置，其他进程的 core 也会落到 OpenClaw 目录里。
建议改用进程级 core 配置，或在关闭开关 / 停止服务时恢复原值。默认关闭这一点应保持。

### P2-4 上传备份把整个文件读进 Lua 内存

`openclaw.lua:1182-1225` 用 `http.formvalue("archive")` 取整份上传（上限 64 MiB）
后再落盘。小内存路由器上并发上传可能 OOM。建议流式处理或在 uhttpd 层压低请求体上限。

## 八、建议的修复顺序

按「后果严重程度 ÷ 修复风险」排序：

1. **P0-1**（backup.sh 暂存目录生命周期）—— 改动最小、收益最直接，先修
2. **P0-2**（`oc_fix_perms` 按目录分类授权）—— 涉及权限模型，必须走完整复核
3. **P1-1**（delpass fail-closed）—— 改动小，但属于安全边界，需正反测试
4. **P1-2**（备份下载 no-follow）—— 与 P0-2 同批，一起改才闭合攻击链
5. **P1-3**（state_dir 校验接线）—— 需要把两份 `oc_state_dir` 合并，注意别破坏升级兼容
6. P2 各项作为后续版本加固

**流程要求**：以上除 P0-1 外全部涉及安全边界/权限/路径解析，按项目约定属「复杂修改」，
必须走 `tools/isolated-review.sh`（Claude 改）→ Qwen 独立复核 → 人工确认 → 应用 → 全量回归。
P0-1 虽是逻辑错误，但影响恢复正确性，也建议走同一流程。
