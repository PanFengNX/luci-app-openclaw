## 2. 高风险问题

### P1-1 `models_url` SSRF

证据：

- `luasrc/controller/openclaw.lua:667-679` 验证 provider 后调用 `models.sh models-url`；
- `root/usr/libexec/openclaw/models.sh:774-881` 从配置读取 Base URL 并请求 `${base}/models`；
- `root/usr/libexec/openclaw/lib.sh:831-867` 的 `oc_safe_url` 主要验证 `http://`/`https://`、空白和命令行参数形状，未拒绝 loopback、私网、link-local、IPv6 本地地址或 DNS 解析后的内网地址。

触发：管理员或可影响 provider 配置的用户把 Base URL 指向 `127.0.0.1`、RFC1918、169.254.169.254、IPv6 loopback 或解析到内网的域名，然后打开模型页。

建议：解析主机并拒绝本机、私网、link-local、未指定地址；处理重定向和 DNS rebinding；最好使用专门的外连 allowlist。应在 OpenWrt/Linux 上用本地 HTTP 服务和内网地址矩阵复现。

### P1-2 恢复事务不完整

证据：

- UCI commit：`backup.sh:725-743`；
- 扩展凭据/插件：`backup.sh:783-810`；
- crontab：`backup.sh:853-875`；
- rollback：`backup.sh:692-709`、`927-955`，当前主要回滚 `data` 与 `cloud/bin`。

触发：恢复过程中扩展凭据、插件复制、网关启动或后续步骤失败。

后果：UCI、`secure/delpass`、`cloud/pass`、`cloud/home`、插件目录或 crontab 可能已改变，而旧状态目录已经回滚，形成混合状态。

建议：为所有外部变更建立 restore journal 和统一安全快照，全部健康检查成功后再提交；失败时统一回滚。现有测试未覆盖该端到端事务矩阵。

### P1-3 `cloud/bin` 权限边界不闭合

证据：

- `cloud.sh:244-253` 创建云目录时只 `chmod`，不统一 `chown root:root`；
- `cloud.sh:256-279` 定位组件，`cloud.sh:364-373` 后续可执行；
- `lib.sh:1764-1805` 的 `oc_harden_root_paths` 收紧 `cloud/home`、`cloud/pass`，但未覆盖 `cloud/` 与 `cloud/bin`。

触发：`oc_fix_perms` 递归把 base 交给服务用户后，服务用户可改写 `cloud/bin`，后续 root 云任务执行该程序。

建议：明确 root-only 矩阵并在每次执行前校验属主、类型、权限、非符号链接；或者完全使用服务用户执行云组件，避免 root 执行不可信路径。

### P1-4 `recover-lock` 未知 rc=0 输出可能放行 doctor

证据：`lib.sh:1670-1726`：锁存在时若 CLI rc=0 且输出不含 `confirm|fingerprint|holder|owner`，设置 `result=0`；`repair.sh:415` 根据 0 继续 doctor。

触发：官方 CLI 返回 rc=0，但输出为空、本地化、结构化或未知格式。

建议：锁存在时默认 fail-closed；只有经官方契约明确证明“无需人工恢复”才返回 0。增加 rc=0 空/未知输出测试。

## 3. 中风险和历史遗留

### P2-1 Lua RUNDIR TOCTOU

`openclaw.lua:229-243` 检查 `/tmp/.openclaw` 后，`api_apply` 约 `702-723` 用 `io.open` 写 keyfile，中间没有目录 fd/no-follow 原子语义。真实利用性未在 OpenWrt 测量。

### P2-2 嵌套 provider 插件可能未归档

`backup.sh:447-463` 复制 `oc_oc_dir()/lib/node_modules/*` 时跳过 `openclaw`；但 `models.sh` 的插件发现支持 `openclaw/node_modules/<plugin>`。需覆盖嵌套布局归档/恢复测试。

### P2-3 未收录云组件哈希继续执行

`cloud.sh:1148-1164`、`1540-1582` 对未收录版本只告警，仍可能下载、安装或执行。建议默认拒绝。

### P2-4 缺少 timeout 时直接执行

`lib.sh:1105-1115`、`install.sh:252-261` 缺少 `timeout` 时退化为直接执行。需在最小 BusyBox 环境验证卡死和锁占用行为。

### P2-5 core_pattern 不恢复

`init.d/openclaw:730-765` 开启 core dump 时修改全局 `/proc/sys/kernel/core_pattern`，停止服务未恢复。

### P2-6 api_run 首 token 授权过宽

`openclaw.lua:781-800` 只校验 `argv[1]`；完整命令形状如 `mcp add`、`devices approve`、`pairing approve` 等仍可能被放行。逐 token 引号只能防 shell 注入，不能限制业务权限。

### P2-7 dist-web 过期发布页

`dist-web/index.html:31-45` 仍指向 `1.0.1-r1.apk`、旧大小和旧 MD5；当前版本为 1.8.57，页面引用文件不存在。发布流程若使用此页会产生 404/错误安装。

### P2-8 README 过时说明

当前 README 已同步模型行为和 1.8.57 安装命令，但仍需进一步核对：

- `root/etc/config/openclaw` 的目录说明与实际默认模板 `root/usr/share/openclaw/config.default`；
- `.env` 应描述为 `<state_dir>/.env`，不能固定写 `~/.openclaw/.env`；
- 备份范围应明确列出 `secure/delpass`、`cloud/pass`、`cloud/home`、`cloud/bin`、插件实际归档和清单文件。

## 5. 官方依据

官方 OpenClaw《迁移指南》要求迁移完整状态目录和工作区，包含 `openclaw.json`、`auth-profiles.json`、`credentials/`、sessions、渠道状态和 workspace；要求使用同一 `OPENCLAW_STATE_DIR`/profile，确保状态目录与工作区归 Gateway 运行用户所有，并对含机密的备份加密。

官方《Gateway lock》要求先运行 `openclaw gateway recover-lock` 检查；确认 holder 已停止后，使用同一 state/profile 执行输出的精确 `--confirm <fingerprint>`。心跳、payload、文件或 lease 变化都必须重新检查，不得手工删除锁。官方页面未在审计材料中给出稳定的 rc=0/非零分类契约，因此本项目未知输出放行路径不能视为安全。
